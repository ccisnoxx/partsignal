# PartSignal GEO 文档治理规则

| 项目 | 内容 |
|---|---|
| 文档状态 | 已批准后方可作为开发输入 |
| 版本格式 | `主版本.次版本` |
| 变更方式 | PR 评审，禁止只改代码不改契约或相关文档 |
| 适用范围 | GEO 监测核心版及其与现有事实、内容、发布、审计模块的集成 |

## 1. 文档状态

每份文档采用以下状态之一：

| 状态 | 含义 |
|---|---|
| 草案 | 可讨论，不可作为实现强约束 |
| 评审中 | 已进入产品或架构评审，允许评论，不应并行实现冲突方案 |
| 已批准 | 可作为开发与验收权威输入 |
| 已实现 | 目标设计已由代码、迁移、契约和测试证明 |
| 已废弃 | 不再适用，必须指向替代文档或 ADR |

建议在落库后给每份文档顶部增加状态字段，并在相关任务完成后从“已批准”改为“已实现”。

## 2. 文档分层

### 2.1 产品层

描述用户、目标、范围、页面和验收，不定义具体表结构或内部函数。

### 2.2 业务层

描述领域对象、业务不变量、状态机、指标公式和跨模块协作，是开发不能自行改变的语义层。

### 2.3 技术层

描述如何在当前技术栈中实现业务层，包括数据、API、前端、后台任务、安全、测试和运维。

### 2.4 交付层

描述实施顺序、任务依赖、任务模板和完成定义。交付层只拆解，不重新解释业务规则。

### 2.5 决策层

ADR 记录已经做出的重要技术决策、替代方案和后果。已接受 ADR 的改变必须新增 ADR，不直接重写历史结论。

## 3. 标识规则

### 3.1 能力 ID

使用 `CAP-GEO-XX`，用于描述稳定产品能力，例如：

- `CAP-GEO-01` 监测对象与别名；
- `CAP-GEO-05` 统一观测批次与运行；
- `CAP-GEO-12` 机会与复测闭环。

### 3.2 需求 ID

使用 `REQ-GEO-领域-序号`，例如：

- `REQ-GEO-SUBJECT-001`；
- `REQ-GEO-RUN-004`；
- `REQ-GEO-METRIC-007`。

### 3.3 任务 ID

使用 `GEO-NNN`。编号按实施阶段分段：

| 范围 | 阶段 |
|---|---|
| `GEO-001`～`GEO-099` | 文档、契约、架构基线 |
| `GEO-100`～`GEO-199` | 监测主数据 |
| `GEO-200`～`GEO-299` | 问题变体、平台与计划 |
| `GEO-300`～`GEO-399` | 批次、运行和人工采集 |
| `GEO-400`～`GEO-499` | API 自动采集 |
| `GEO-500`～`GEO-599` | 分析和人工复核 |
| `GEO-600`～`GEO-699` | 指标、洞察和报告 |
| `GEO-700`～`GEO-799` | 机会、任务和复测 |
| `GEO-800`～`GEO-899` | 浏览器采集试点 |
| `GEO-900`～`GEO-999` | 生产硬化和上线验收 |

### 3.4 测试 ID

使用 `TEST-GEO-类型-序号`，类型包括：

- `UNIT`
- `INT`
- `CONTRACT`
- `E2E`
- `SEC`
- `PERF`
- `OPS`

## 4. 变更控制

以下变化必须同时更新 PRD、业务文档、技术文档、契约和测试：

- 新增或删除核心业务状态；
- 改变指标分子、分母、过滤条件或最低样本；
- 改变采集方式可比性规则；
- 改变原始答案或人工复核的不可变性；
- 改变机会关闭和复测规则；
- 新增外部平台自动化采集；
- 新增敏感凭据或浏览器会话存储方式；
- 改变数据保留或删除规则。

## 5. 代码与文档同步要求

每个功能 PR 至少核对以下内容：

```text
[ ] OpenAPI 是否更新
[ ] database contract 是否更新
[ ] Alembic migration 是否新增且可前滚
[ ] 业务状态机文档是否更新
[ ] 页面和操作是否更新
[ ] 测试矩阵是否更新
[ ] 实施任务状态是否更新
[ ] ADR 是否需要新增
```

## 6. 不允许的文档实践

- 用实施计划中的临时说明覆盖已批准业务语义；
- 只在代码注释中记录关键指标公式；
- 在多个页面文档分别维护不同状态机；
- 以截图作为接口和数据契约；
- 删除 ADR 历史以伪装“从未做过某个决策”；
- 使用“智能判断”“综合评分”等无法验收的模糊表述；
- 把尚未批准的平台自动化能力写成已经支持。
