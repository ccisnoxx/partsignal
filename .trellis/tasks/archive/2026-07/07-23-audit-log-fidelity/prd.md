# 审计日志高保真复刻与审计闭环

## 1. 背景

当前 PartSignal 已有 PostgreSQL `audit_logs`、服务端成功审计写入、管理员列表接口和简化版 `/audit` 页面，但与已批准原型及真实审计闭环存在明显差距：页面只有四列；查询仅支持对象过滤；没有详情、模块、执行结果、失败/权限拒绝事件；原始 JSONB `details` 被直接返回；时间、身份和请求链路的展示契约不完整。

本任务不是另建审计系统，而是在现有唯一审计表和写入服务上完成全局审计日志工作台，并按用户确认的边界补齐关键业务命令的结果审计。

## 2. 目标

以附件 `1581 × 995` 原型作为已批准视觉与交互规格，在现有 PartSignal 审计体系上完成“审计与安全 > 审计日志”页面、真实组合查询、服务端详情、安全变更摘要和关联入口。审计记录必须由服务端真实操作产生，以 PostgreSQL 为唯一权威来源，只追加、不可由业务接口修改或删除，且不泄露敏感信息。

## 3. 用户与权限

- 全局审计列表、筛选和详情只允许当前 `ADMIN` 账号访问，保持现有权限边界。
- `ENGINEER` 不显示入口；直接请求列表或详情由服务端返回 `PERMISSION_DENIED`。
- 关联入口只提供导航，不授予额外权限；目标页面和目标 API 必须再次执行既有权限校验。
- “拒绝”审计仅指已认证用户的账号类型拒绝。未登录、失效会话、强制改密和 CSRF 失败属于访问安全日志，不写业务审计。

## 4. 范围

### 4.1 页面与交互

- 复用现有 AppLayout，在 `/audit` 显示“审计与安全 / 审计日志”、标题和真实不可变说明。
- 高保真还原两行筛选、关键字/重置行、记录总数、自动刷新、手动刷新、十列表格、分页和右侧详情。
- 筛选状态、页码和每页数量写入 URL；选中详情使用页面局部状态，关闭后主表恢复宽度。
- 桌面以 `1581 × 995` 为第一优先；窄屏沿用项目现有 Table 横向滚动和 Ant Drawer，不重新设计移动信息架构。

### 4.2 查询

- 服务端支持时间、操作者、业务模块、动作、对象类型、执行结果、请求 ID、关键字、分页的组合筛选。
- 时间 API 使用 UTC date-time；边界为半开区间 `[created_from, created_to)`；前端固定按 `Asia/Shanghai` 展示。
- 请求 ID 为精确匹配；它是相关 ID，不承诺数据库唯一。
- 关键字仅检索对象标识和服务端明确允许的非敏感摘要字段，不扫描完整请求、任意 JSONB 或敏感载荷。
- 排序固定为 `created_at DESC, id DESC`，保证刷新和翻页顺序稳定。

### 4.3 自动刷新

- 用户显式开启后每 30 秒刷新当前筛选和当前页；默认关闭。
- 页面不可见时暂停，重新可见后由 TanStack Query 正常刷新；不在后台高频请求。
- 刷新替换当前查询结果，不在前端追加或去重；保留筛选、页码和所选详情。
- 手动刷新立即请求当前列表；如详情打开，同时刷新详情。
- 失败必须显示现有错误状态，不能继续宣称数据已更新。

### 4.4 详情、安全摘要和关联入口

- 详情再次执行管理员权限和服务端安全投影，不假设列表响应已经足够安全。
- 展示时间、操作者、当前账号类型、业务模块、动作、对象、请求 ID、结果、变更摘要、结果说明和关联入口。
- 变更摘要只使用写入时保存的白名单字段；没有旧值的历史记录显示“历史未记录”，不得回查当前对象反推。
- Prompt、API Key、Header 值、授权信息、Cookie、令牌、密码、内部 Prompt、第三方响应和完整业务快照均不得写入或返回。
- 关联入口仅覆盖已有明确路由的对象类型；不存在、归档或当前无权访问时显示明确状态，不修改历史审计内容。

### 4.5 审计业务闭环

- 成功事件继续与业务变更在同一事务提交；审计写入失败必须回滚成功业务变更。
- 失败/拒绝事件只能在业务事务回滚后用同一审计模块、同一表独立提交；不得把失败记录混进已回滚事务。
- 执行结果表示“该业务命令的执行结果”，取值只允许 `SUCCESS | FAILED | DENIED`；不把下游对象状态或 HTTP 状态猜成结果。
- 失败记录只保存稳定错误码和受控用户说明，不保存异常堆栈、SQL、请求正文或第三方原始响应。
- 创建命令失败时对象尚未生成，`target_id` 可以为空，页面明确显示“未创建”；不得伪造对象 ID。
- 本任务只给原型点名的九类关键命令补齐失败/拒绝结果；该范围已于 2026-07-23 获用户确认。

### 4.6 九类关键命令

1. 更新或启停平台配置。
2. 激活平台规则版本。
3. 保存平台 Prompt。
4. 内容审核通过或退回。
5. 创建发布登记或登记发布结果。
6. 新增 GEO 观测。
7. 删除发布账号（当前没有发布账号启停命令，不在本任务发明）。
8. 停用或启用用户。
9. 提交产品事实审核。

九类操作的现有 action、调用点和差异见 `research/audit-coverage-matrix.md`。不得为填充页面增加静态事件或重复 action。

## 5. 数据和身份规则

- `audit_logs` 继续是唯一权威表；不新增第二张审计表、事件流或缓存状态。
- 新增业务模块、命令结果和安全结果说明的持久化契约；原有 `action` 仍是唯一事件标识，不新增第二套 action 枚举。
- 操作者以 `actor_id` 为权威。名称和账号类型沿用项目既有“当前用户目录投影”：用户存在时显示当前值，缺失时显示“已删除用户/账号类型未记录”；不声称为事发时快照。
- 当前没有系统任务/服务账号审计身份契约。本任务不虚构系统用户，也不把后台任务 ID 当作人工操作者。
- 客户端 `X-Request-ID` 缺失时继续由服务端生成 UUIDv4；提供时必须满足长度与允许字符约束，重复值允许用于跨服务关联。
- 数据库和 API 保持 UTC；前端固定北京时区展示，避免依赖浏览器本地时区。

## 6. 敏感信息规则

- 写入端由字段白名单定义审计摘要形状；现有键名黑名单保留为第二道阻断，但不再作为唯一保护。
- 读取端按 action/模块的已知安全结构投影，列表和详情都不得直接透传任意 `details`。
- 自由文本默认不进入可搜索摘要；确有业务价值的说明必须先经过长度限制和敏感边界审查。
- 失败结果只保存稳定 `error_code` 和受控 `result_message`；不直接保存任意异常消息。
- 敏感字段只记录“字段发生变化”“已配置/未配置”或计数，不记录明文、密文、哈希或可逆片段。

## 7. 性能与保留

- 列表和总数均由 PostgreSQL 参数化查询完成，前端不得全量加载后筛选。
- 保留现有 `(target_type, target_id, created_at DESC)` 索引；为稳定全局时间分页增加 `(created_at DESC, id DESC)` 的最小索引。
- 其他操作者、action、result、request ID 索引只在实现阶段用代表性 `EXPLAIN (ANALYZE, BUFFERS)` 证明需要后增加，不预建索引集合。
- 关键字不引入 `pg_trgm`、全文搜索服务或 Redis；先在可见时间范围内查询对象 ID 和白名单摘要。
- 当前没有保留期限契约。本任务不增加归档、清理或删除能力，继续无限追加；后续保留政策必须单独评审。

## 8. 约束

- 不使用 ImageGen，不改变原型字段、顺序、信息架构或增加视觉装饰。
- 不新增无必要依赖、第二套审计表、事件枚举、平行写入框架、Redis 业务状态、WebSocket、消息队列、Outbox、搜索服务或通用动态对象路由。
- 不使用 Mock、静态假数据、固定成功路径、虚构事件或静默默认值。
- 不从当前对象重算历史，不把完整对象快照返回前端。
- 公共 API、数据库、权限、审计语义变化必须同步更新 OpenAPI、database contract、生成类型、测试和权威方案文档。
- 本规划阶段不执行 `task.py start`，不修改业务代码、契约或数据库。
