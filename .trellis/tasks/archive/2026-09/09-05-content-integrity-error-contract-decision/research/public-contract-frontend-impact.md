## Findings

### 1. 公共合同基线

1. `ErrorEnvelope` 是唯一 wire model：`error` 包含必需的 `code`、`message`、`details`、`request_id`，而 `ErrorDetail.code` 仍是开放 `string`；`details` 是开放 object，默认 `{}`。证据：`contracts/openapi.yaml:4162-4206`、`backend/app/schemas/common.py:169-181`、生成类型 `frontend/src/shared/api/generated/schema.d.ts:2106-2117`。
2. `error_response()` 将 `AppError` 的 code/message/details 与 `request.state.request_id` 写入信封；HTTP middleware 为每个请求生成或接受合法 `X-Request-ID`，并把同值写回响应头。证据：`backend/app/errors.py:23-53`、`backend/app/main.py:261-295`。因此公共领域错误必须保持 `error.request_id == X-Request-ID`；worker 没有 HTTP request ID，不能套用 HTTP request policy。
3. `error_responses(*status_codes)` 只为调用方显式列出的 status 绑定 `ErrorEnvelope`，不会自动推断 409/500。证据：`backend/app/errors.py:15-20`、`backend/app/main.py:153-230`。T4 只复用已有 operation 的 409，不需要因为新增运行时 code 而新增 schema；若决定稳定 JSON 500，则必须另行 contract-first，当前 stable spec 明确禁止把默认 500 body/code/header/media type 固化为公共合同（`.trellis/spec/backend/error-handling.md:155-187`）。
4. 当前相关 operation 的静态/runtime status set 已冻结，且测试禁止 500、`default`、`4XX`：

   - `createContentTask`、`createManualContentVersion`、`createContentRevision`、`createPublishedContentRepairTask`、`submitProductFactReview`：成功 201 + 401/403/404/409/422 + 400；`backend/tests/unit/test_contract.py:245-259`，`backend/tests/unit/test_runtime_response_metadata.py:294-300,327-345`。
   - `createGenerationJob`、`createHumanizationJob`、`retryGenerationJob`：成功 202 + 401/403/404/409/422 + 400；`backend/tests/unit/test_contract.py:263-267`、`backend/tests/unit/test_runtime_response_metadata.py:327-331`。
   - `submitContentVersion`、`approveContentVersion`：成功 200 + 401/403/404/409/422 + 400；`backend/tests/unit/test_contract.py:213-219,341-344`。
   - `replaceProductFactsDraft`：成功 200 + 401/403/404/409/422 + 400；`backend/tests/unit/test_runtime_response_metadata.py:295,298`。

   每个已声明非成功 status 都引用 `#/components/responses/ErrorResponse`，generated client 也只把它们生成为 `components["responses"]["ErrorResponse"]`，不会生成 code union。示例：`frontend/src/shared/api/generated/schema.d.ts:8239-8272,8680-8818,9070-9137`。
5. `backend/tests/unit/test_contract.py:37-98,100-315` 和 `backend/tests/unit/test_runtime_response_metadata.py:639-695,1020-1055` 的职责是合同/metadata 形状和精确 status 集；它们不能证明某个数据库 race 的业务 code。只有公共 status 集变化、ErrorEnvelope 形状变化或新增稳定 500 时才需要修改这些 metadata/contract 断言。新 code 在当前开放 `string` 中不要求 generated schema diff，但应由行为测试、Frontend V2 文档和稳定错误处理 spec（若规则变化）冻结。

### 3. 推荐合同集合与同步结论

#### 3.1 应映射或重放

- `uq_content_tasks_idempotency_key`：同 identity replay；异 identity 复用 `IDEMPOTENCY_CONFLICT` / 409 / `{}`，message 保持 `幂等键已用于另一内容任务创建请求`。

#### 3.2 应保持 unknown 或 worker 显式失败

- `uq_content_versions_source_job_id`：worker 显式标记 Job `FAILED`，现有公开 `error_code/error_summary` 字段承载失败投影；不产生 HTTP 409，不 replay。
- `uq_content_versions_task_id`：HTTP unknown 500；worker FAILED；不改号、不 replay。
- `uq_content_versions_one_approved_per_task`：HTTP unknown 500，整笔 approval rollback；不伪装 revision/state 409。
- `uq_fact_versions_product_id`：HTTP unknown 500，整笔 submit rollback；不伪装 pending/revision。

CHECK、NOT NULL、不可变 trigger、缺失/未知 diagnostics 和未被本命令 allowlist 确认的其他 IntegrityError 同样保持 unknown；不得解析数据库 message。该边界来自 `.trellis/spec/backend/error-handling.md:76-100,155-187`。

#### 3.3 OpenAPI/runtime/generated/frontend 文档是否同步

- **无结构同步的情况**：继续使用现有 operation 的 409、统一 ErrorEnvelope、`request_id`、`details={}`，或保持未知 500 默认 boundary，均不改 `contracts/openapi.yaml`、runtime metadata、`schema.d.ts`。原因是相关 operation 已有 409，且 `ErrorDetail.code` 是 `string`，不是 code enum；generated client 仅需重新生成验证而非产生 diff。Humanization 现有合同属于此类。
- **必须同步的情况**：若产品批准新的 `CONTENT_REVIEW_PENDING`（或其他新公共 code）并要求稳定前端行为，应更新 stable error-handling spec、Frontend V2 facts/content review policy、backend integration/HTTP tests 与 frontend fixtures/tests；只有改变 status、ErrorEnvelope/details 形状、加入 code enum 或声明稳定 500 response 时，才修改 OpenAPI、runtime metadata、generated client。严格按 `OpenAPI -> runtime/service -> backend tests -> generated -> frontend -> specs/docs` 顺序。
- **不应同步的情况**：未知 500 不得在 OpenAPI 增加 500 response、不得在 runtime metadata 为 operation 猜测 500、不得在 generated client 增加 `INTERNAL_ERROR`，不得让 frontend 将它当作 revision stale。此点由 `backend/tests/unit/test_runtime_response_metadata.py:792-794,1033-1055` 和 stable spec `:164-167` 约束。

- 未执行 PostgreSQL race、HTTP 请求或 frontend test；本文件是公共合同审计，不证明数据库 race 可达性、锁序或最终 constraint 诊断。实现任务必须以真实 current-head PostgreSQL 证明替代 mock-only 结论。

- `uq_content_tasks_source_published_content_issue_id` 的 row 在 T4 清单内，但其 command、router、前端宿主属于 publication owner；本 T4-C 只冻结公共影响，不建议越界实现或修改 publication/GEO 合同。实现顺序应由 T5-C/T5 implementation 决定。
- `CONTENT_REVIEW_PENDING` 是公共 code 候选而非现有已批准 code；在 T4-C review 前不得写入 production mapper、OpenAPI enum 或 generated union。若产品选择复用 `INVALID_STATE_TRANSITION`，需重新冻结准确 message、details 和 content review 前端行为。
