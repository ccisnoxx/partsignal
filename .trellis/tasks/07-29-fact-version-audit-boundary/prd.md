# 修复事实版本审计边界

## 目标

修复 DEF-02：从某个事实版本打开“审核与历史”时，只展示该事实版本自身的追加式审核记录，不能把同产品其他事实版本的记录混作当前版本历史。

## 背景与已确认事实

- 验收产品 `d73c7434-0ce5-47b5-ac94-072936cc4279` 同时存在 PUBLIC V1 `b90171fe-083e-4639-ba1a-c96b3554c301` 与 RESTRICTED V2 `0c2a0b2e-275d-4d7f-92f9-dddc726599bc`。
- 验收截图中 V2 弹窗的事实版本 ID 正确，但审核时间线出现明确标记为 V1 的事件。
- `FactReviewRecord.fact_version_id` 是审核记录的父版本外键；事实状态命令同时把业务审计写为 `target_type="FactVersion"`、`target_id=<当前事实版本 ID>`。
- 当前读取投影按 `product_id` 和 `version <= 当前版本` 聚合同产品旧版本，和写入归属不一致。
- 当前没有产品级事实审核时间线 API 或分区 UI；全局审计查询已经能按 `target_type + target_id` 精确过滤。

## 需求

1. `GET /api/v1/fact-versions/{fact_version_id}/review-context` 的 `review_history` 只返回 `fact_version_id` 与路径参数完全相同的审核记录。
2. V1、V2 的审核记录和 `audit_logs` 继续保持追加式、不可变，不迁移、不改写、不删除历史数据。
3. 事实版本状态转换继续以 `FactVersion` 和当前版本 UUID 作为审核记录及审计日志的权威 owner。
4. 前端继续以选中的事实版本 ID 请求审核上下文，并直接展示服务端返回的当前版本历史；不得在前端增加兼容过滤或产品级拼接。
5. 保持内容版本的任务级累计审核历史、全局审计查询、审计筛选及其他模块行为不变。
6. 只修复 DEF-02，不处理 CSV、标签校验、GEO 更正、审计动作筛选或其他验收偏差。

## 验收标准

- [x] 同一产品创建 V1、V2，并为两个版本分别产生不同审核事件和对应 `FactVersion` 审计事件。
- [x] 读取 V2 审核上下文时，`review_history` 每项 `target_id` 都等于 V2 ID，且不包含只属于 V1 的事件。
- [x] 读取 V1 审核上下文时，V1 自身历史仍完整正确，不包含 V2 事件。
- [x] 前端从 V2 行打开“审核与历史”时请求 V2 的 `review-context`，界面不展示仅属于 V1 的事件。
- [x] 审计事件继续使用 `target_type="FactVersion"` 与对应版本 UUID；没有产品级时间线冒充版本级历史。
- [x] OpenAPI 响应结构、数据库结构和历史数据均不变化；仅把 `review_history` 的既有语义明确为“目标事实版本自身历史”。
- [x] 针对性后端集成测试、前端组件测试、契约检查及受影响层静态检查通过。

## 范围外

- 新增产品级事实时间线或把产品级与版本级历史并列展示。
- 修改内容版本的任务级累计审核历史。
- 修改共享审计筛选、审计工作台或其他 DEF 项。
- 数据库迁移、历史数据修复、兼容字段或模糊 fallback。

## 公共契约影响

响应字段和类型不变，但 `review_history` 的数据范围会从“同产品截至当前版本”收窄为“路径所指事实版本自身”。这是对公开 API 语义的修正，需在实施前获得用户对本规划摘要的明确批准。
