# 阶段五：行为保持的代码结构改善

## Goal

在阶段一至阶段四最新实现上进行可分片回归、可随时停止的结构改善，降低大型 Router、集中 `models.py` / `schemas.py`、跨模块状态操作和前端大型页面的维护成本，同时保持全部外部行为与业务语义不变。

## Requirements

- 保持 OpenAPI、数据库结构和语义、状态值与状态机、权限、错误码、审计规则、幂等语义、并发控制、事务边界和用户可见行为不变。
- 继续采用模块化单体；PostgreSQL 是唯一业务状态来源，Redis 只承担既定 Celery 消息职责。
- Router 只负责 HTTP 输入输出、认证依赖、CSRF / Cookie 等协议语义和领域错误到 HTTP 错误的映射。
- 应用服务负责事务、状态转换、跨实体权限门禁、行锁与乐观锁、幂等键、审计协调和必要的外部调用协调。
- 每个业务不变量只有一个权威实现位置；先删除重复实现，再决定是否提取共享实现。
- 不创建只转发参数、简单重命名或只包装一行调用的 Service、Repository 或 Helper。
- 前端只使用 OpenAPI 生成类型，不新增第二套请求或响应契约。
- 仅在存在稳定职责边界和测试收益时拆分文件，不要求所有模块使用同一分层模板。
- 不引入微服务、DDD 框架、通用 Repository、Unit of Work、事件总线、插件系统、Factory / Strategy 体系、通用工作流引擎或全局 CQRS。
- 不新增迁移，不修改 `contracts/openapi.yaml` 或 `contracts/database.md`；如实现中发现必须改变公共契约、数据库或状态机，立即停止并单独请求确认。
- 保留阶段一至阶段四和用户当前未提交改动，不清理、不覆盖、不回退无关成果。

## Acceptance Criteria

- [ ] 重构前基线已实际运行，关键状态转换、权限、并发、幂等、审计与 HTTP 映射有特征测试保护。
- [ ] 发布查询与命令职责清晰，重复投影、文件校验归属和跨 Router 导入已消除，行为不变。
- [ ] AI / 平台配置、产品事实、内容策划与生产、身份、文件和 GEO 的状态写入由各自应用服务统一协调。
- [ ] Router 不再直接提交核心状态转换，但仍保留 FastAPI 路由声明、依赖注入、请求解析、响应构造和错误映射。
- [ ] `schemas.py` 按真实领域边界拆分，调用方直接导入权威 Schema，不保留兼容性重导出层。
- [ ] `models.py` 按真实领域边界拆分，`models/__init__.py` 仅确保映射注册；Alembic 与运行时 metadata 表数和 mapper 数保持一致且无循环导入。
- [ ] 有明确收益的前端大型页面完成物理拆分，查询键只有一处定义，缓存失效语义和 UI 行为保持不变。
- [ ] `docs/architecture.md`、`docs/development.md`、`docs/testing.md` 及受影响的代码注释或 docstring 与最终职责一致。
- [ ] 契约检查、lint、typecheck、后端单元与 PostgreSQL 集成、前端组件、构建、E2E、Compose / 迁移历史 / preflight 验证通过；无法在本地完成的环境验证有明确说明。
- [ ] 最终差异审计未发现第二来源、隐藏回退、薄包装、重复业务逻辑、未说明的行为变化或新增迁移。
