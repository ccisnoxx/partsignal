# 昨日改动全站回归测试

## Goal

对 2026-08-04 的功能代码改动建立可复现、可归因的全站回归结论，找出真实缺陷并明确其严重度、根因、影响范围和验证证据，避免把既有问题或环境故障误判为昨日改动。

## Background

- 昨日主要功能提交为 `e426d7b`（全站业务表格操作流程重设计，84 个文件，新增 4717 行、删除 942 行）和 `949dc98`（受约束删除引导，51 个文件，新增 1282 行、删除 196 行）。
- 改动跨越数据库迁移、后端模型/Schema/路由/服务、OpenAPI 与数据库契约、前端页面/共享组件、单元/集成/E2E 测试，属于共享业务工作流和跨层契约变更。
- 用户已观察到“新增平台请求数据不符合接口契约”“AI 渠道获取模型失败”和“批准内容点击开始发布后没有后续”三个现象；是否由昨日改动引起，必须通过提交差异、复现和失败归因确认。
- 原任务要求 `make verify` 作为完成门禁，Session 72 摘要声称完整验证通过，但同一 journal 的 Testing 段未记录实际命令或结果；本任务必须重新取得独立、可追溯的验证证据。
- 原任务验收面包含 25 张业务表，以及事实审核、内容单主线、发布版本切换、GEO 优化回流、配置治理和七类受约束删除；本次回归矩阵以原 PRD、设计、实施计划和目标操作矩阵为基线。
- 规划、归档和开发日志提交只用于恢复上下文，不作为产品回归目标。

## Requirements

- R1：以 `e426d7b` 和 `949dc98` 的实际差异、对应 Trellis 任务文档及昨日会话记录确定回归矩阵，不凭页面名称猜测范围。
- R2：验证数据库迁移、OpenAPI/运行时 Schema/前端生成类型一致性，以及昨日触及的服务端状态转换、权限、删除阻断和动作投影。
- R3：验证昨日触及的前端工作台、主要操作、更多操作、删除引导、AI 渠道模型管理及跨页面导航；浏览器检查必须执行真实交互，而不是仅启动服务。
- R4：先运行最能直接证明改动行为的定向测试，再按共享契约风险运行必要的契约、集成和 E2E 检查；完整构建和全量套件是否必要由实施计划按风险明确。
- R5：每个失败必须记录命令或操作、期望、实际结果、相关提交/文件位置及归因；只修复证据确认属于本任务范围的问题。
- R6：保留用户当前改动，不使用真实或已泄露的第三方 API Key，不在日志、测试、截图或任务文档中保存凭据。
- R7：对确认由昨日提交引入的缺陷，在同一任务内修复权威根因、补充最小回归测试并复验所有受影响调用方；不得以 UI 兜底、静默默认或兼容分支掩盖服务端合同问题。
- R8：用户已批准修复 Hostdzire 的 Docker hairpin 防火墙缺口；放行范围覆盖所有 Docker bridge，但只允许访问宿主机自身公网 IP 的 TCP 443，并验证其他宿主机端口仍保持阻断。

## Technical Notes

- 昨日差异没有修改新增平台表单的请求组装、`PlatformProfileCreate` 写入 Schema 或域名规范化器；该现象仍需复现和定性，但不能在没有提交归因证据时当作昨日回归修复。
- 昨日 AI 改动为渠道/模型治理投影和模型发现响应增加 `workflow_stage`、`primary_task`、`configured`，前端发现弹窗改为直接消费该 typed 响应；实际出站 `GET {base_url}/models` 和 Bearer 鉴权边界未改动。回归必须分别验证“本地 typed 响应链路”和“外部供应商/凭据失败”，不能混为一个问题。
- 原任务是数据库、OpenAPI、后端投影和前端消费的单发布单元；本次回归及修复保持同一任务顺序推进，不提前拆分未知缺陷为子任务。
