# 全站表格操作流程：业务设计基础

## 1. 业务闭环

```text
产品事实维护与审核
→ 内容任务、草稿和内容审核
→ 人工发布、结果登记与首次核验
→ 只读发布成果与发布后问题
→ GEO 人工观测、洞察和优化回流
```

配置中心、业务设置、用户和审计为该闭环提供治理能力，不是平行的内容生产流程。

## 2. 行操作必须回答的问题

对每张表、每一种业务阶段依次回答：

1. 这行代表待办、工作对象、不可变成果、分析结果，还是配置对象？
2. 用户看到它时，最应该完成的下一件业务任务是什么？
3. 完成这一步后，对象进入什么状态或哪个下游流程？
4. 哪些动作只是查看、低频维护或危险清理，应降为次级？
5. 哪些历史只能追溯，不能被原地修改？
6. 如果页面没有合理下一步，是正常终态、等待外部平台、缺少前置条件，还是产品流程缺口？

## 3. 五类操作模型

| 类型 | 主操作原则 | 次级操作 | 禁止模式 |
| --- | --- | --- | --- |
| 待办队列 | 推进当前节点 | 查看依据、取消或关闭 | 用“查看详情”掩盖待办 |
| 工作对象 | 继续当前工作 | 历史、低频维护 | 固定 CRUD 不随阶段变化 |
| 不可变成果/证据 | 查看追溯或发起新流程 | 导出、关联查看 | 原地编辑或删除历史 |
| 分析结果 | 下钻证据或发起优化 | 筛选、打印 | 只显示数字且无行动路径 |
| 配置治理 | 完善、测试、启用等治理下一步 | 编辑、停用、受约束删除 | 把配置 CRUD 当业务闭环 |

父级表单中的行内输入矩阵不是独立业务对象，不为了视觉一致增加操作列。

## 4. 设计权威顺序

```text
业务目标与不变量
→ 对象生命周期和当前阶段
→ 用户下一步任务
→ 服务端命令/导航/下钻合同
→ typed action 投影
→ 前端操作层级与文案
```

现有代码、路由和 token 只用于识别迁移成本与可复用能力，不能排在业务流程之前。

## 5. 已批准原则

- D1：每行主操作表达当前最重要的下一步业务任务，不以资源 CRUD 为中心。
- 查看、资料编辑、停用和删除默认属于次级操作，除非它们就是当前业务阶段的主要任务。
- D2：采用“任务入口优先、简单命令直达”；复杂或需要判断的操作进入权威工作区，危险与不可逆命令必须确认。
- D3：事实版本一旦被退回即成为历史结论；处理退回意见后必须从事实工作区冻结新版本，不允许原样重提。
- D4：全部业务界面、产品讨论和验收使用中文状态名称；英文枚举只属于技术合同。
- D5：产品事实工作区是唯一草稿；提交时直接冻结待审核版本，同一产品最多一个待审核版本。
- D6：每个内容任务只有一条当前内容版本主线；产品可以通过多个内容任务并行产出多篇文章。
- D7：一篇文章、一个具体平台、一个独立内容任务；同一产品可以并行拥有多个任务。
- D8：首次核验成功前，实质改稿经重新审核后继续原发布工作并追加版本切换事件；不关闭重建。
- D9：正常发布成果的主操作为“开始产品观测”，入口预选产品并核对该产品全部合格文章。
- D10：具有明确异常依据的 GEO 洞察可以创建可追溯的独立优化内容任务；宽泛聚合只下钻明细。
- D11：配置类表格按当前治理阶段显示主操作；配置不完整时完善配置，尚未验证时测试，验证通过但未启用时启用，正常运行时进入运行或管理入口。服务端投影治理阶段和下一步，前端不自行猜测。
