## Findings

### 1. 权威来源、命名与 diagnostics 结论

- 当前运行时 metadata 的命名约定在 `backend/app/db.py:12-19`：`uq_%(table_name)s_%(column_0_name)s`。因此未显式命名的 `(task_id, version)`、`(source_job_id)`、`(product_id, version)` 分别落为 `uq_content_versions_task_id`、`uq_content_versions_source_job_id`、`uq_fact_versions_product_id`；当前 ORM 也在 `backend/app/models/content.py:96-108`、`backend/app/models/product_facts.py:65-79` 声明了这三个唯一性 owner。
- 九条约束的初始 schema owner 是冻结 `backend/app/migration_schema_v1.py:304-314`、`:426-495`（0001-0008 历史不可修改）；当前 schema 增量由 `backend/alembic/versions/0032_content_task_idempotency.py:15-33`、`0034_publication_workflow_redesign.py:724-737`、`0035_business_workflow_primary_tasks.py:174-198` 建立或补齐。`contracts/database.md:37,43,217,414-421` 是当前不变量合同。
- PostgreSQL `UNIQUE` constraint 与 `UNIQUE INDEX` 均以 `sqlstate=23505` 报告冲突；对真实 psycopg exception，`error.orig.sqlstate` 与 `error.orig.diag.constraint_name` 是可结构化读取的候选字段。唯一索引（包括 partial unique index）在当前测试中通过 `diag.constraint_name` 返回索引名：`backend/tests/integration/test_generation_reliability.py:687-705` 已对 `uq_generation_jobs_idempotency_key`（constraint）和 `uq_generation_jobs_active_humanization_source`（index）作真实 PostgreSQL 断言。
- mapper 只能同时检查 `sqlstate == "23505"` 和精确最终名称；禁止读取 `str(error)`、`orig.message_primary`、英文错误文本、请求字段猜测或任意 23505 fallback。`backend/app/services/content_production.py:353-365` 是现有 humanization 的正确技术形状，且现有合同明确要求保留 `uq_generation_jobs_idempotency_key` 与 `uq_generation_jobs_active_humanization_source` 的既有映射：`.trellis/spec/backend/error-handling.md` 的“生成自然化作业唯一约束领域映射”场景。
- CHECK、NOT NULL、不可变 trigger 和未列名 FK 不属于本九条；它们不能借由唯一约束 mapper 猜测。NOT NULL 通常只有 table/column diagnostics、不可变 trigger 的 `RAISE EXCEPTION ... ERRCODE='55000'` 通常没有可用 constraint name。父任务 companion matrix 使用 `not_null:<table>.<column>` 作为审计键是合理的，但不应把它们放入本次 public unique mapper。
- 当前应用没有全局 IntegrityError handler：`backend/app/main.py:247-259` 只注册 `AppError` 和 `RequestValidationError`；`backend/tests/unit/test_runtime_response_metadata.py:1050-1054` 明确断言 `IntegrityError not in app.exception_handlers`。因此父任务 `research/database-constraint-matrix.md` 中把未知 IntegrityError 描述为“全局 409 REVISION_CONFLICT”的部分已过时；当前未捕获异常默认由框架返回 500（不应改变为全局 revision 映射）。

### 3. 事务、错误信封、前端与同步面的共同合同

- 已知 HTTP mapper 必须在最终 `flush` 的异常边界 rollback 后抛 `AppError`；`ErrorEnvelope` 固定 `{error: {code, message, details, request_id}}`，`request_id` 由 `backend/app/errors.py:40-53` 从 request state 注入。唯一可定位字段时才使用 `details.errors[].loc=["body", field]`；本九条中的 task/source issue/pending 状态通常没有需要定位的 body field，`details={}` 是当前既有域合同。未知错误原样抛出，由默认 500，不返回数据库 constraint/index 名。
- Content Task create 成功路径是 add task → flush →（若 `commit=True`）commit（`content_planning.py:402-423,426-464`）；任何 idempotency conflict 都必须无 task/revision/audit 副作用。Repair task 成功路径 issue/platform/fact 校验 → add task → flush → commit（`publication.py:895-950`）；冲突不能部分写 issue revision、task 或 audit。当前这些命令未在成功路径追加 AuditLog；不要为 mapper 加失败 AuditLog。
- Generation Job HTTP caller 的事务 owner 是 request `DbSession`；`_create_job` 不应自行 rollback。成功 commit 后才 `_dispatch_job`（`content_production.py:463-510,589-593,730-734`）；已知冲突、未知异常不得 dispatch。Humanization 的既有 conname mapper必须保持：`uq_generation_jobs_idempotency_key` 通过 canonical identity replay/IDEMPOTENCY_CONFLICT，`uq_generation_jobs_active_humanization_source` 为 `HUMANIZATION_ALREADY_ACTIVE`；不能将 HTTP policy 搬到 worker。
- Generation worker 使用独立 `SessionLocal`（`generation.py:339-342`）。版本 INSERT、task.current pointer、task.revision、job `SUCCEEDED`/content_version_id 是一批原子提交（`:419-463`）；任一 IntegrityError 先 rollback，再只把 job 标为 FAILED 并 commit（`:473-486`）。worker 不生成 HTTP response/request ID，不应返回 `409`；Redis/Celery 只传 job UUID，不承担唯一性 authority。
- Content review `submit-review` / `approve` 的根 owner 是 request session，content/task lock 和 `db.commit()` 在 `review.py:351-411`。`approve` 还涉及旧 approved → SUPERSEDED、目标状态/revision、`ContentReviewRecord`、SUCCESS Audit；partial-index 失败必须整体 rollback，不能让旧版本已 superseded 或留下 review/audit。`current_content_version_id` 只有创建/worker 成功时推进，review conflict 不得移动 pointer。
- Fact review submit 的根 owner 是 request session，product lock、FactVersion INSERT、`FactReviewRecord` 和 commit 在 `product_facts.py:669-715`；partial pending 冲突必须 rollback 全部。`replaceProductFactsDraft` 的 product workspace 更新（`:633-657`）不触发本九条，不能给它添加 fact-version mapper。
- OpenAPI 当前相关 operation 已声明 409/422 response：`createContentTask` `planning.py:284-289`、生成操作 `production.py:216-222,243-248,308-313`、content submit/approve `production.py:541-570`、fact submit `product_facts.py:287-292`；ErrorEnvelope 的 generated shape 是 `frontend/src/shared/api/generated/schema.d.ts:2106-2117`。若 T4-C 新增公共 code/message，必须同步 `contracts/openapi.yaml`、runtime metadata tests、generated client 和相关 Frontend V2 文档；本审计不修改这些文件。
- 前端当前行为是 generic message + request ID：content task mapper 只按结构化 `details.errors` 定位表单字段并在 `IDEMPOTENCY_CONFLICT` 清除本地 key（`frontend/src/domains/content/content.api.ts:469-509`、`new-content-task-page.tsx:141-167`）；AI production 在幂等冲突时清除 command key，其他 409 展示错误并刷新条件分支（`content-ai-production.tsx:149-187`）；content review 只按 `details.errors[].loc` 绑定 comment，否则展示 form message（`content-review.model.ts:27-58`）；fact workspace 已对 `FACT_REVIEW_PENDING` 或 `INVALID_STATE_TRANSITION` 做恢复分支（`frontend/src/domains/product/fact-workspace-page.tsx:205`）。新 `CONTENT_REVIEW_PENDING` 若获批，必须新增精确 code 分支/测试，不能让 generic 409 意外自动重试。

### 5. 父任务 research 的事实偏差/缺口

- `research/database-constraint-matrix.md:102-120` 和 `database-constraint-companion.csv:157,171` 把 `uq_fact_versions_product_id`、`uq_fact_versions_one_pending_per_product` 的 owner 写成 `product_facts.replace_product_facts` / `replaceProductFactsDraft`。这是错误的：该 command 只更新 `products` workspace（`product_facts.py:633-657`）；真实 FactVersion INSERT 在 `submit_fact_review`（`:660-715`）及 operation `submitProductFactReview`（`routers/product_facts.py:287-310`）。

### 6. 推荐后续 implementation Task 与依赖顺序

按稳定 command owner 和独立可验证目标拆分，不建立全局 registry、通用 mapper framework、repository 或第二套错误类型系统：

1. `content-task-idempotency-integrity-mapping`：只处理 `createContentTask` 的 `uq_content_tasks_idempotency_key`，固定同 identity replay、异 identity `IDEMPOTENCY_CONFLICT`、request/error envelope 与真实 PG race。无前置依赖；建议作为第一个实施任务。
2. `generation-job-integrity-mapping`：处理 GENERATE create/retry 的 `uq_generation_jobs_idempotency_key`，同时保持已完成 Humanization 两条映射；补 caller rollback/canonical replay 与真实 worker boundary 回归。依赖 1 的合同风格确认，但不依赖其代码。
3. `content-version-identity-integrity`：只处理 `uq_content_versions_task_id` 与 `uq_content_versions_source_job_id`，覆盖 manual/revision、AI worker、job FAILED/no second version；默认 unknown/worker `GENERATION_FAILED`，若 T4-C 批准新 public code 必须先改本任务 decision。依赖 2 的 worker diagnostics fixture 可复用但不得共享 mapper。
4. `content-version-review-uniqueness`：只处理 pending/approved 两个 partial unique index；若批准 `CONTENT_REVIEW_PENDING`，本 task 同步 OpenAPI/runtime/generated/frontend contract；验证 `submitContentVersion` 与 `approveContentVersion` 的全事务 rollback。依赖 3（先冻结版本 identity/worker failure semantics）。
5. `fact-version-integrity-mapping`：只处理 `submitProductFactReview` 的 `uq_fact_versions_product_id`（unknown）与 `uq_fact_versions_one_pending_per_product`（既有 `FACT_REVIEW_PENDING`）；不得改 `replaceProductFactsDraft`。依赖 1 的 diagnostics/unknown test conventions，和 3/4 可代码上独立，建议在 content tasks 完成后实施。

推荐实施顺序为 1 → 2 → 3 → 4 → 5；每项独立提交/验证，父任务再统一审计 OpenAPI/runtime metadata/generated client/Frontend V2 文档以及与 T5-C publication/GEO 范围的边界。当前本研究没有运行代码测试，也没有修改生产代码、合同、测试、stable spec、数据库或生产数据。

## Caveats / Not Found

- 未连接或操作真实 PostgreSQL；除现有 migration/integration source 证据外，本审计没有重新执行 catalog 查询或制造九条约束的竞态。`sqlstate=23505` 与 `diag.constraint_name` 的 index 行为应在每个 implementation task 的 real-PG test 中再次断言。
- 未发现九条约束对应的全局 mapper、公共 code 注册表或 generated enum；当前 generated `ErrorDetail` 只允许任意 string code 和 details map（`frontend/src/shared/api/generated/schema.d.ts:2109-2117`），新增稳定 code 是否需要更窄 schema 属于 T4-C contract decision，不能从现状推断。
- 未发现 `content_versions` pending/approved unique index 的现有真实 diagnostics 测试；现有 content review 测试主要覆盖正常状态、revision 和审核历史，不能证明 partial-index race 或 rollback。
- 未发现 repair-task source issue 的真实 unique diagnostics 测试；publication command 的 service/route owner 已核实，但该范围属于 publication service，后续 implementation 必须避免把 T5-C publication/GEO 约束带入本任务。
- 当前 shell 缺少 `sqlalchemy`，无法直接 import `Base.metadata`；最终名 `uq_content_versions_task_id`、`uq_content_versions_source_job_id`、`uq_fact_versions_product_id` 由项目 naming convention 与 frozen/current declarations 推导，并与父 matrix 记录一致，仍以 PostgreSQL catalog 为最终验证。
- 不应把 `uq_content_versions_task_id`、`uq_fact_versions_product_id` 的 allocator race 改写为 `REVISION_CONFLICT`；也不应把 CHECK、NOT NULL、55000 trigger 或未列名 FK 作为本九条的唯一 mapper。未知边界默认显式 500/worker FAILED 是有意的合同选择，不是失败吞掉。
