# PartSignal GEO 产品愿景与范围

| 项目 | 内容 |
|---|---|
| 文档版本 | V1.0 |
| 文档状态 | 目标设计 |
| 核心用户 | 公司内部 GEO、市场、产品、FAE、内容和管理人员 |
| 产品定位 | 电子元器件与国产替代业务的 GEO 情报与运营平台 |

## 1. 产品愿景

PartSignal 的目标不是成为通用 AI 写作工具，也不是只记录员工在 AI 平台上搜索结果的表格系统。

目标产品应持续回答：

> 主流 AI 平台如何认识公司的品牌、产品型号和国产替代关系；这种认识是否准确、稳定、具有竞争力；公司应该采取什么行动改善它。

一句话定义：

> **监测 AI 如何认识公司的产品，并持续改善这种认识。**

## 2. 核心业务价值

### 2.1 对市场和 GEO 运营

- 知道哪些用户问题能够自然发现公司产品；
- 知道公司与竞品在不同平台和问题中的提及、推荐和引用差距；
- 知道哪些来源正在影响 AI 的答案；
- 将趋势下降和竞争异常转化为可执行机会。

### 2.2 对产品和 FAE

- 发现产品参数、封装、认证、应用条件和替代关系错误；
- 区分“产品未被发现”和“产品被错误描述”；
- 使用已批准事实版本作为核验依据；
- 保留每次判断的回答、引用和人工复核证据。

### 2.3 对内容和渠道运营

- 识别未覆盖问题、弱引用领域和竞品信源优势；
- 从机会直接创建内容任务、事实修订或发布修复；
- 将已发布内容与后续复测关联；
- 避免只按内容数量评价 GEO 工作。

### 2.4 对管理层

- 观察重点产品的监测覆盖、可见率、推荐率、准确性和风险处理情况；
- 了解投入后是否出现持续、同口径的相关变化；
- 对每个数字都能下钻到原始证据。

## 3. 目标用户场景

### 场景 A：自然可见度

用户提出非点名问题，例如“某进口型号有哪些国产替代方案”。系统需要判断公司产品是否自然出现、是否被推荐、排名和竞品情况。

### 场景 B：品牌事实与声誉

用户点名公司或型号提问。系统需要检查回答是否正确、是否遗漏关键边界、是否引用权威来源。

### 场景 C：竞品差距

同一组问题中竞品持续被推荐。系统需要展示竞品依赖的主要信源、问题覆盖和推荐理由，并生成差距机会。

### 场景 D：内容发布后的复测

某项内容任务完成并形成发布成果。系统按冻结的基线问题和采集配置发起复测，展示前后差异但不声称单一因果。

### 场景 E：风险处理

系统发现严重错误声明。运营人员查看原回答和引用，产品人员核验后创建事实修订或纠错内容任务，并保留处理链路。

## 4. 产品边界

### 4.1 核心版范围

```text
监测对象与别名
→ 问题主题与变体
→ AI 观测面和采集配置
→ 监测计划与重复采样
→ 观测批次和单次运行
→ 原始回答、截图和引用
→ 提及、推荐、竞品和声明分析
→ 人工复核
→ 可解释指标和趋势
→ 机会、任务和同口径复测
```

### 4.2 与现有 PartSignal 的关系

| 现有能力 | GEO 核心版如何复用 |
|---|---|
| `Product` | 自有产品身份和详情入口 |
| `FactVersion` | 声明准确性核验的权威事实快照 |
| `QueryTopic` | 稳定问题主题；新增问题变体而非复制问题库 |
| `ContentTask` | 内容缺口和优化机会的行动载体 |
| `PublishedArticle` | 干预和文章关系观测的发布成果 |
| `PublishedContentIssue` | 已发布页面异常和修复链路 |
| `FileRecord` | 截图、导出和采集证据 |
| `GeoObservation` | 保留现有文章关系观测，不直接改造成回答级运行 |
| `AuditLog` | 高价值配置、规则、机会和复测动作审计 |

### 4.3 核心版非目标

- 多租户、收费和客户门户；
- 自动替代产品事实审核；
- 大规模无授权浏览器爬取；
- 传统 SEO 全套工具；
- 自动发布到全部外部平台；
- 统一、不透明 GEO 分数；
- 通过一次前后对比宣称因果；
- 用外部模型自动覆盖人工复核结论；
- 将 Redis、浏览器本地状态或统计快照作为业务事实源。

## 5. 产品成功标准

核心版上线后，应能够稳定回答以下问题：

1. 某公司产品在指定时间、平台和问题集合中的自然可见率是多少；
2. 它是否被推荐，推荐位置和稳定性如何；
3. 哪些竞品在相同条件下表现更好；
4. AI 引用了哪些自有、竞品和第三方来源；
5. 哪些产品声明错误、部分正确或无法判断；
6. 哪些数据因样本不足、采集失败或人工未复核而不可下结论；
7. 哪些异常已经转化为任务，任务处理到什么阶段；
8. 干预后同口径复测有什么变化；
9. 任意指标能否下钻到原始问题、答案、引用、截图、分析版本和人工复核；
10. 管理员能否知道自动监测为何失败、是否产生外部调用和是否可以安全重试。

## 6. 产品阶段

| 阶段 | 能力目标 | 是否可业务使用 |
|---|---|---|
| R1 主数据与计划 | 能设计和预览监测矩阵 | 仅配置 |
| R2 人工运行框架 | 能系统保存回答级人工观测和证据 | 可进行受控人工试用 |
| R3 API 自动观测 | 能按计划自动运行受控 API 采集 | 可形成持续监测基础 |
| R4 分析与复核 | 能形成可追溯提及、推荐、引用和准确性结果 | 可用于日常运营 |
| R5 洞察和机会 | 能发现趋势、异常并转化任务 | 核心版业务闭环成立 |
| R6 浏览器试点 | 能对一个批准的真实产品界面进行采集 | 提升代表性，不替代人工核验 |

## 7. 关键产品原则

1. **原始证据永远先于指标。**
2. **事实准确性优先于单纯提及。**
3. **非点名自然可见度与点名声誉分开。**
4. **人工、API、浏览器结果不静默混合。**
5. **重复采样优于单次结论。**
6. **指标必须可解释、可下钻。**
7. **机会必须能形成行动和复测。**
8. **自动化采集必须合规、可控、可停。**
