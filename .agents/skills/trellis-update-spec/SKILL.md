# 维护项目规范

先判断已有实现、类型、测试或权威文档是否已经充分表达该知识；一次性细节无需重复成规范。读目标正文，更新同一所有者，避免新建平行版本。

实现合同写到对应层 spec；跨领域思考提示才放 guides。使用项目真实路径，不假设存在 `src/templates/` 或 CLI 上游专用目录。

按变化内容写清必要证据：

- API/命令：实际签名、字段、约束、失败语义及相关验证。
- 数据/迁移：状态所有者、完整性、不兼容变化与回滚条件。
- 团队决策：适用触发、选择理由和能改变决策的条件。

格式遵循现有文档。矩阵、示例和好/坏对照仅在能消除歧义时使用，不要求每次七节齐全或固定例子数量。

新增规范时更新相应索引，确认引用可用、与代码证据一致且没有重复合同。未形成新约定时无需为了结束任务修改 spec；写文档也不自动授权提交或发布。
