# 全项目功能回归测试（第二轮）

## 1. 目标

对当前 `main` 的 PartSignal 全项目重新执行一轮功能、业务逻辑与 UI/UX 回归，建立可追溯的新质量基线。测试范围覆盖全部当前路由、核心业务链路、状态机、角色、表单、操作反馈和跨页面一致性；24 张业务表、全部操作列、13 个 DELETE 接口及其直接业务链路作为高风险重点，而不是范围上限。

本任务只执行测试并提交矩阵、缺陷和最终报告。发现的产品、测试门禁、环境或文档问题均不在本任务内修复，后续按共同根因另行立项。

## 2. 已确认背景

- 第一轮全项目验收已完成，后续已分别修复验收门禁、部分产品 UI/UX 缺陷、前端测试门禁和开发环境 Vite API 代理。
- 历史结果包括后端集成 `68 passed`、前端 `175/175` 与视觉合同 `23/23` 连续两轮通过、隔离 E2E `52/52`；这些只用于确定回归重点，本轮不得继承其通过状态。
- 当前清单基线为 24 张业务表、58 个可变长文本槽和 OpenAPI 中 13 个 DELETE 接口；执行开始时必须按当前代码与合同刷新，新增或移除项不得漏测。
- 历史缺陷 `PS-QA-001`～`PS-QA-004`、`PS-QA-101`～`PS-QA-110` 及表格展示问题需要验证未回归。
- 历史 `PS-QA-201`～`PS-QA-203` 尚缺少关闭证据，涉及菜单取消后的焦点恢复、面向用户的“物理删除”术语、AI Header 删除影响说明，列为本轮优先验证假设，最终状态以本轮运行证据为准。
- `docs/deployed-full-functional-acceptance-plan.md` 的内容任务删除条件与当前 `contracts/database.md` 存在口径漂移；本轮按当前合同和实现判定，并将文档差异记为产品/文档决策项，不在本任务中修改。

## 3. 范围内需求

### R1. 新基线与可追溯清单

- 记录提交、迁移 head、服务版本、执行环境、浏览器版本、运行时间和统一 `run-id`。
- 从 `frontend/src/app/App.tsx`、OpenAPI、数据库合同、状态机和当前实现重新生成路由、角色、接口、表格、操作列与删除清单。
- 所有测试项初始状态必须是 `NOT_RUN`；旧报告只能提供待复测线索。

### R2. 开发环境与自动化门禁

- 先验证 Compose 前端 `/api` 代理、匿名会话探测、真实登录和容器重启后的可用性。
- 重新运行合同、单元/组件、PostgreSQL 集成、隔离 E2E、lint、类型检查和构建门禁，记录通过数、失败数、跳过数、耗时和清理状态。
- 失败先归因；本任务继续执行不依赖该失败的测试，不修改产品代码或现有测试来恢复门禁。

### R3. 全业务流程与状态机

- 覆盖认证/会话、总览、用户与权限、平台与 Prompt、AI 配置、产品与事实、内容任务与生成、审核、发布与异常修复、GEO、文件和审计。
- 执行 W0～W6：基础配置、产品/事实、内容生产、发布、异常修复/GEO、恢复性与跨页面一致性。
- 验证合法与非法状态转换、旧 revision、重复提交、并发变化、迟到响应、刷新/后退/重登后的最终状态。

### R4. 全路由功能与 UI/UX

- 覆盖当前全部可达路由及动态路由变体，不仅检查页面能打开，还要执行主要功能和真实请求。
- 检查加载、空、失败、无权限、只读、保存中、成功和重试状态，以及术语、层级、操作优先级、危险动作说明和反馈。
- 验证桌面、移动、主题、真实 200% 缩放、键盘、焦点恢复、reduced-motion、滚动、弹窗、Tooltip 和对比度。

### R5. 24 张业务表与全部操作列专项

- 对执行时仍存在的全部业务表逐项验证数据、搜索、筛选、排序、分页、总数、空/错状态、详情返回、长文本、固定列和内部滚动。
- 盘点并执行每个当前声明的操作；行为随状态变化的动作覆盖各真实分支，公共实现不机械重复无意义组合。
- 验证允许、禁止、取消、确认、加载、防重复、成功、结构化失败、缓存刷新、跨页面结果和鼠标/键盘焦点。

### R6. 13 个 DELETE 接口专项

- 覆盖用户、产品、事实版本、内容任务、发布账号、发布记录、GEO 人工观测完整更正链、平台类型、平台 Prompt、平台、AI 渠道、AI Header、AI 模型。
- 每项验证权限/CSRF、最小合法删除、状态或引用阻断、重复 DELETE、并发双请求或确认期间状态变化、数据库原子性、关联历史、附件清理调度、审计和前端缓存一致性。
- 删除测试使用隔离、可重建的开发数据；不得以环境可重建为由跳过服务端权限、历史保护和输入验证。

### R7. 历史缺陷回归

- 对已修复项重新复现原步骤，取得本轮独立证据，不能只引用原修复任务的测试结果。
- 对 `PS-QA-201`～`PS-QA-203` 以及第一轮未覆盖的删除并发、确认期间状态变化、迟到响应/缓存和全部操作列键盘链进行重点补测。
- 新缺陷使用本轮独立编号，重复历史缺陷则保留原编号并记录“回归/仍存在”。

### R8. 报告与后续任务输入

- 输出覆盖矩阵、表格/操作/删除专项矩阵、缺陷清单和最终报告。
- 每项只使用 `PASS`、`FAIL`、`BLOCKED`、`NOT_RUN`、`NOT_APPLICABLE`；`BLOCKED` 和 `NOT_APPLICABLE` 必须有证据或合同依据。
- 缺陷按共同根因归组，给出严重程度、影响、最短复现、期望/实际、证据及建议的权威修复位置，但不实施修复。

## 4. 范围外

- 不修改后端、前端、数据库迁移、合同、产品文档、现有测试或部署配置。
- 不在本任务中修复产品缺陷、测试门禁、环境阻断或文档漂移。
- 不创建新的通用测试框架、页面对象层或长期自动化抽象；优先复用现有测试、脚本和探针。
- 不对生产环境执行写入或破坏性测试，不负责发布或部署验收。
- 不做渗透、容量、压力或第三方平台真实发布专项；认证、权限、CSRF 和敏感数据展示仅按产品功能合同测试。
- 没有专用测试凭据时不调用真实第三方 AI；本机 OpenAI-compatible 测试边界仍属于范围内。

## 6. 约束与决策

- 当前阶段使用开发环境，允许对本轮拥有且可重建的隔离数据执行真实删除。
- 旧结果不继承为通过；本轮发现缺陷也不影响“测试和报告任务”本身按真实结果完成。
- 产品是否统一由服务端 `available_actions` 驱动全部固定操作仍是待决策项；除合同已有明确要求外，本轮不把设计偏好直接判为缺陷。
- 测试设施阻断达到可复现后停止重复运行，继续独立模块；修复另行立项。
