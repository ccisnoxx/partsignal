# 昨日改动全站回归测试：技术设计

## 1. 设计结论

本任务不再设计一套测试框架，也不先假设所有当前故障都来自昨日改动。回归以提交 `e426d7b`、`949dc98` 和原任务验收矩阵为基线，依次验证合同、数据库与服务端状态、前端 typed 消费、真实浏览器流程；每个失败经过提交归因后，才进入最小根因修复。

原任务把数据库约束、OpenAPI、后端投影和前端消费作为单发布单元，本次测试与修复也保持单任务顺序推进。未知缺陷不提前拆成子任务，避免重复搭建环境和在问题尚未归因时制造跨任务依赖。

## 2. 权威基线

- 产品行为基线：原任务 `prd.md` 与 `research/target-action-matrix.md` 中 25 张业务表、D1—D11 和受约束删除增补。
- 技术基线：原任务 `design.md`、`implement.md`、`contracts/openapi.yaml`、`contracts/database.md`。
- 稳定开发约束：`.trellis/spec/backend/available-actions-contract.md`、`.trellis/spec/frontend/component-guidelines.md` 及受影响层的其他有效规范。
- 代码差异基线：`git diff e426d7b^..949dc98`；规划、归档和 journal 提交不作为产品回归目标。
- 当前行为基线：实际测试输出、API 错误信封、数据库约束结果、Playwright trace/截图和浏览器 console/network；不以“昨日已通过”的摘要替代证据。

## 3. 回归数据流

```text
提交差异与原验收矩阵
        ↓
合同生成/静态门禁
        ↓
后端定向单元与迁移/集成测试
        ↓
前端定向组件与页面测试
        ↓
现有 Playwright 真实业务流程
        ↓
失败复现 → 根因与提交归因 → 最小修复 → 定向复验
        ↓
make verify 全量完成门禁
```

每一层只证明自己的边界：OpenAPI 证明字段形状，后端测试证明状态和权限，前端测试证明 typed token 的渲染与操作，E2E 证明真实用户流程。任何一层不得用 mock 成功替代下一层的真实行为。

## 4. 回归矩阵

### 4.1 合同与静态一致性

- OpenAPI、FastAPI 运行时 Schema 和生成的 `schema.d.ts` 无漂移。
- `workflow_stage`、`primary_task`、`available_actions`、`deletion` 均保持 required typed 合同。
- 后端 Ruff/mypy 与前端 ESLint/TypeScript 通过，未知 token 不通过默认分支静默降级。

### 4.2 数据库与服务端业务

- `0035_business_workflow_primary_tasks` 的合法前滚、歧义阻断、当前内容版本指针、发布核验版本快照和不可逆降级。
- 产品事实、内容单主线、发布版本切换/关闭/核验、GEO 优化来源、AI/平台治理阶段、用户与删除引用投影。
- 列表与详情复用同一投影规则，命令写入重新校验状态、权限、revision 和引用；不得产生 N+1 或相信旧 token。

### 4.3 前端业务工作台

- 产品事实、内容任务/版本、发布工作/成果/问题、GEO 观测与洞察、AI 渠道/模型、平台/平台类型、发布账号、用户和审计页面。
- 每行唯一主操作、更多菜单、危险确认、删除条件下钻、错误反馈、焦点返回，以及桌面/移动/200% 缩放等价能力。
- 页面只消费 typed 投影，不用本地状态、角色或关联字段重建业务流程。

### 4.4 两个已报告现象

- 新增平台：复现真实 payload 和 422 `details.errors`，确认是前端输入边界、服务端合同还是既有问题；昨日差异未触及创建 payload 与域名校验，不能跳过归因直接修改。
- AI 渠道获取模型：用项目的显式 OpenAI-compatible 假服务验证 Bearer、`GET {base_url}/models`、`data[].id`、发现响应的 `configured/primary_task` 和前端弹窗；外部第三方只做无凭据连通性证据，不使用已泄露或其他真实密钥。

### 4.5 获批的 Hostdzire 防火墙边界

当外部 AI FQDN 在 Hostdzire 解析为宿主机自身公网 IP 时，Docker bridge 回连进入 INPUT 链。修复只允许 `docker0` 与 `br-*` 访问该公网 IP 的 TCP 443，不绑定单个 Compose 网段，也不开放 22、80 或其他宿主机端口。持久规则以 `/etc/iptables/rules.v4` 为权威，并与运行时规则、跨项目容器请求及公网健康检查共同复验。

### 4.6 内容批准后的发布主入口

服务端 `primary_task=START_PUBLICATION` 已正确表达当前主动作，缺陷只在前端动作目标：内容版本行必须进入 `/publications?content_version_id=<version-id>`，发布工作台从服务端 `publication-ready-items` 中精确恢复该版本并打开既有开始发布确认表单。继续发布和查看成果仍按 `content_task_id` 进入已有发布工作，不复制发布表单或写命令。

## 5. 失败归因与修复规则

每个失败在任务 `report.md` 记录：检查命令/交互、期望、实际、首次失败输出、相关文件与提交、归因和处理结果。

归因顺序：

1. 在未改代码的基线上稳定复现一次。
2. 追踪失败字段或动作到一个权威所有者，并检查所有调用方。
3. 对照 `e426d7b^..949dc98` 判断失败路径是否由昨日改动引入。
4. 只有证据确认属于本任务时才修复；环境、外部供应商、既有缺陷和偶发失败分别记录，不扩大范围。
5. 修复放在共享根因所有者，删除过时逻辑；不新增兼容分支、静默 fallback、重复投影或第二状态源。
6. 添加能在修复前失败、修复后通过的最小回归检查，然后复验全部直接调用方。

同一失败只有在代码、配置或环境发生预计会影响结果的变化后才重跑。连续修补若没有新根因证据，立即停止并报告阻断。

## 6. 测试隔离与安全

- 单元测试使用项目现有 fixture；集成测试使用 Compose 测试服务；E2E 脚本创建独立临时数据库、显式本地 AI 假服务和临时对象存储，并由 trap 清理。
- 不修改共享开发/预发布业务数据，不调用应用部署或迁移命令，不使用真实第三方凭据；只执行用户明确批准的 Hostdzire 防火墙边界修复。
- 现有 Playwright Test Runner 用例优先。只有失败需要临时交互判断时，创建 `yesterday-regression-audit-*` 命名会话；所有会话必须单独关闭，并以 `playwright-cli list --all --json` 核验。
- 浏览器产物只保留能证明缺陷的 trace、截图或请求摘要，不保存 Cookie、API Key、敏感 Header 或响应正文中的私密数据。

## 7. 报告与文档

- `report.md` 是本任务的测试证据与缺陷台账，不复制稳定业务合同。
- 若修复改变功能、状态、API、数据库或配置行为，同步更新对应权威合同/设计/spec；本次基础设施边界变更同步更新 Hostdzire Runbook 与 infra spec。
- 最终交付列出通过项、修复项、非本次问题、未执行项和剩余风险。

## 8. 回滚

- 每个修复保持最小独立 diff；定向复验失败时回到该缺陷的根因分析，不叠加第二个猜测补丁。
- 不执行数据库降级；若迁移本身有缺陷，只修改前滚迁移/测试并在隔离数据库重新验证。
- 不自动提交或推送。完成验证后另行向用户展示提交范围并取得确认。
