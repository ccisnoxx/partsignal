# 技术设计

## 1. 设计结论

本任务不是再造一套视觉系统，而是在既有 macOS 双主题框架内补齐两种业务页面形态：集合工作区与详情工作区。实现复用现有路由、`PageHeader`、`TableRegion`、Ant Design 和全局 CSS，只在页面语义确实不同的位置调整 JSX 结构与共享布局类。

不拆父子任务。集合页与详情页共同依赖默认页头密度、业务表面、断点和浏览器验收矩阵；拆分会重复修改 `global.css` 和测试环境，不能形成更小的独立交付。

## 2. 现状证据与根因

- `frontend/src/shared/components/PageHeader.tsx:8-27` 已统一标题、面包屑和操作，默认页头可通过共享 CSS 收紧，无需新增第二个页头组件。
- `frontend/src/features/product-facts/ProductsPage.tsx:31-42`、`frontend/src/features/content-tasks/ContentTasksPage.tsx:25-31` 等集合页使用无标题 Card 包裹 Table，页头、Card 和表格形成重复边界。
- `frontend/src/features/configuration/AIChannelsPage.tsx:40-82` 为每个渠道渲染最低约 310px 的 Card；它适合少量展示，不适合并列比较配置状态。
- `frontend/src/features/content-editor/ContentEditorPage.tsx:146-170` 先把工作区分成 `16/8`，再在左侧平分 Markdown 与预览，使两个主要阅读面板在桌面端仍偏窄。
- 同页后续还有差异、事实、追溯、历史和修订区块，见 `frontend/src/features/content-editor/ContentEditorPage.tsx:171-289`；问题是定位成本，不是数据缺失。
- `frontend/src/features/product-facts/ProductFactsPage.tsx:117-125` 已有粘性章节导航和保存条，证明章节锚点是项目内可复用模式。
- `frontend/src/app/App.tsx:30-55` 已为所有详情提供稳定路由。引入 Finder 式同页详情会增加选中项、URL、加载、返回和焦点恢复状态，违反单一导航来源。

## 3. 共享布局模型

### 3.1 集合工作区

```text
紧凑页面上下文：标题 / 简介                         主操作
┌──────────────────────────────────────────────────────┐
│ 筛选、搜索或 Tabs                                    │
├──────────────────────────────────────────────────────┤
│ 单一主要数据表面：Table / 行式列表                   │
│ 状态、关键字段、详情入口、行操作                     │
└──────────────────────────────────────────────────────┘
```

- 默认 `PageHeader` 保留现有 API，只通过 `.page-header:not(.page-hero)` 收紧字号、上下间距和描述宽度；工作台 Hero 不受影响。
- 数据集外层统一使用 `.collection-panel`；继续保留承担标题、`extra`、提示、错误、空态或加载职责的 Ant Card DOM，只调整边距、阴影和边界，不新增 `CollectionPage` 包装组件。
- 搜索、筛选、Tabs 与所属 Table 视觉相连；不在一个页面中叠加多个无标题 Card 边框。
- `TableRegion` 继续拥有宽表横向滚动和可访问区域语义；不新增移动卡片渲染分支。
- 每屏只保留一个视觉主操作，现有次级和危险操作继续使用 Ant Design 层级。

### 3.2 详情工作区

```text
紧凑页面上下文：面包屑 / 标题 / 状态
粘性章节导航或操作条（仅长页面）
┌──────────────── 主内容区 ────────────────┬─ 决策/上下文 ┐
│ 正文、表单、表格或对照                   │ 状态与操作   │
└──────────────────────────────────────────┴──────────────┘
次级区块按既有业务顺序继续进入文档流
```

- 详情模板是共享 CSS 网格，不是强制页面组件。短详情页可以保持单列或两列，只有真实并列内容才使用多列。
- 内容任务和 AI 渠道详情直接复用 `.form-section-nav` 的锚点模式，并为目标区块设置 `scroll-margin-top`。不引入新的 SectionNav 组件。
- 内容审核使用一个 `.review-toolbar` 同时承载原生章节链接和现有 `available_actions` 按钮，并与 `.form-section-nav` 共享同一组玻璃表面、边框和阴影声明，避免两个 sticky 区域互相遮挡；普通详情卡片保持不透明。
- 不给次级区块设置固定高度或内部纵向滚动，避免主页面与 Card 双重滚动。

## 4. 集合与配置页设计

### 4.1 已有 Table 的页面

适用范围：产品、内容任务、人工发布、GEO 观测、用户、平台类型、平台、平台规则、Prompt、审计日志、业务设置中的目标问题和平台账号。

- 保留查询、列、字段、分页、展开行、筛选、Tabs、Modal 和 mutation。
- 给主要数据容器增加统一集合语义类，移除不承载标题或操作层级的重复 Card 视觉；需要 Card API 的页面可保留 DOM，仅通过类调整边框和内边距。
- 表格密度沿用现有约 36px 控件与 10–12px 单元格垂直内边距，不缩小正文到 12px 以下。
- 人工发布保留三个 Tabs 与摘要条；每个 Tab 的 Table 使用相同集合表面，不把三类记录合并。
- GEO 指标、发布摘要等属于页面上下文，不转成表格，也不改变指标计算或链接。

### 4.2 AI 渠道列表

将卡片网格改为现有 Ant Design Table，并复用 `TableRegion`。列按现有卡片阅读顺序组织：

1. 渠道名称与详情链接。
2. 启停状态。
3. API 根地址。
4. 请求超时。
5. API Key 配置状态与更新时间。
6. Header 数量。
7. 已启用模型标签。
8. 启停与删除操作。

长 URL 与模型 ID 允许在单元格内换行，并保留完整 `title`。模型数据已存在于渠道列表响应，不新增查询或聚合接口。详情链接仍使用 `/configuration/ai/channels/:channelId`，不增加行选中详情或抽屉。

## 5. 详情与审核设计

### 5.1 内容审核

桌面宽屏采用 12 列网格：

- Markdown：5 列。
- 安全预览：4 列。
- 决策依据：3 列。

摘要保持在网格上方。审核操作从会滚走的大页头区域移动到唯一的 `.review-toolbar`，仍直接映射同一个 `available_actions`，原按钮、状态、禁用和 mutation 不变。正文、差异、冻结事实和审核历史始终提供锚点；生成追溯和人工修订的链接与目标使用相同条件渲染。

不把 Markdown 与预览改成 Tabs：审核需要同时对照。也不折叠事实与历史：这些信息属于审批证据，不应默认隐藏。

### 5.2 产品事实与内容任务

- 产品事实保留现有工作区/版本 Tabs、章节导航和底部保存条；主要调整默认页头、表面边界、导航偏移和桌面内容宽度，不重写大表单。
- 内容任务详情保留“任务约束 → 生成输入 → 追溯 → 内容版本”的业务顺序；只为始终存在的任务约束、生成输入和内容版本增加章节锚点，并保持生成输入占更宽主列。
- 表单字段、动态列表、验证、保存、生成和取消入口不变。

### 5.3 AI 渠道与发布详情

- AI 渠道详情保持连接与凭据、Header、模型三个区块；增加章节锚点并统一详情表面，不把表格塞入窄侧栏。
- 发布记录、发布异常和修复任务通常只有一至两个主要区块，只应用紧凑页头与详情表面；不为了模板一致而强行增加三栏或章节导航。

## 6. 响应式矩阵

| 视口 | 集合页 | 内容审核 | 其他详情 |
|---|---|---|---|
| 1440px | 完整列，局部表格滚动兜底 | `5:4:3` 三栏，决策区粘性 | 按职责单/双列 |
| 1024px | 保留 Table，次要列可依 Ant scroll 查看 | Markdown/预览双列，决策区全宽 | 双列能容纳则双列，否则单列 |
| 768px | TableRegion 横向滚动，工具栏可换行 | 单列，操作条不遮挡内容 | 单列 |
| 375px | 单列页头，主要按钮至少 44px | 单列，章节导航横向滚动 | 单列 |

断点继续使用项目已有 767/1199px 体系；仅当 1440 三栏需要时补一个围绕 1400px 的最小媒体查询，不建立新的断点系统。

## 7. 路由、状态与契约

```text
现有 URL → 现有页面查询 → 现有 Ant 组件与业务操作
                         ↓
                    新布局类 / 新 DOM 编排
```

- 不改 `App.tsx`、`routeLoaders.ts`、`routePrefetch.ts`、query key、API 客户端、OpenAPI 类型或 mutation。
- 不新增集合选中状态、URL 参数、Provider、Context 或本地持久化。
- 详情返回继续依赖现有 Link、navigate 与浏览器历史。
- 加载、错误和空状态仍由现有共享组件拥有。

## 8. 样式与可访问性

- 所有新样式消费 `theme.ts` 注入的现有 CSS 变量；不得硬编码主题颜色、阴影或玻璃值。
- 默认页头、集合表面、详情网格、章节导航和粘性操作条集中在 `global.css`，feature 文件只声明语义类和结构。
- DOM 阅读顺序与视觉顺序一致；三栏只用 CSS Grid 布局，不用 `order` 重排。
- 章节导航使用原生链接并有可访问名称；目标区块保留顺序标题。
- 移动端主要按钮至少 44px；宽表继续由可聚焦 `TableRegion` 承载。
- 深浅主题分别检查边框、文字、焦点、粘性表面与滚动阴影；颜色不作为唯一状态提示。

## 10. 测试与验收

- 单元测试验证 AI 渠道行仍展示全部字段、链接和操作；审核页仍展示所有区块、状态与按钮；章节导航指向真实区块。
- 不在 jsdom 中断言像素或 CSS Grid 尺寸。
- 现有 MVP E2E 已登录并访问产品、配置、内容审核和发布页面；在这些既有路径中增加 `scrollWidth <= clientWidth`、主要操作可见、详情 URL/返回和代表性表格区域存在等最小断言，不复制一套数据准备。
- 真实浏览器在 375/768/1024/1440、浅/深主题与 200% 缩放下检查布局、表格局部滚动、章节锚点、粘性区和键盘顺序。
- 不恢复截图快照、PNG 基线或新视觉测试框架。

## 11. 取舍与回滚

拒绝以下方案：

- Finder 同页主从：会制造第二套详情状态、深链接和返回逻辑。
- Tabs/Collapse 隐藏审核区块：降低证据可见性并改变阅读顺序。
- 通用页面构建器或 Schema 布局：当前只有两个稳定布局原语，不值得引入抽象层。
- 新字体、GSAP、虚拟列表或 UI 依赖：现有平台能力足够，且没有性能证据支持新增依赖。

回滚按三个独立步骤反向应用精确 diff：共享布局样式、AI 渠道表格、审核工作台。不得恢复卡片与表格双实现，也不得使用 `reset --hard`、`checkout --` 或 broad clean。
