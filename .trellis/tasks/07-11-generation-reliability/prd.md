# 生成作业可靠性与可观测性

## Goal

确保生成作业从数据库提交到供应商调用和终态落库的全过程可恢复、不会重复调用，并能在 Worker、Beat 或 Broker 故障时被及时发现和定位。

## Requirements

- PostgreSQL 继续作为生成作业唯一权威来源，Redis 只传递作业 ID。
- 数据库提交后即使首次 Broker 投递失败，超龄 `PENDING` 作业也必须自动恢复，不能永久卡住。
- 重复投递、并发 Worker 和恢复任务不得造成同一作业重复调用供应商或创建多个内容版本。
- 只有尚未被 Worker 认领的超龄 `PENDING` 可以自动补投递；`RUNNING` 租约过期后必须显式失败且不得自动重放，用户重试继续创建新作业。
- 不承诺供应商调用与本地终态提交之间的分布式 exactly-once；供应商已接收请求但 Worker 在成功落库前崩溃时，原作业失败且不自动再次调用。
- 作业租约必须严格大于作业快照中的供应商超时与必要收尾裕量；真正失联的 Worker 仍需在明确上界内失败。
- 暴露 Worker/Beat 存活、最老 `PENDING`/`RUNNING` 年龄、失败码和供应商耗时等信号，不记录 Prompt、响应正文或凭据。

## Acceptance Criteria

- [ ] 故障注入“提交成功后、首次投递前进程退出”，作业可在限定时间内恢复执行。
- [ ] 重复消息和并发恢复只发生一次供应商调用，只创建一个 `ContentVersion`。
- [ ] 供应商调用后、成功落库前 Worker 崩溃时，原作业在租约后失败且不会自动产生第二次调用；显式重试形成新的可追溯作业。
- [ ] 最大合法供应商超时期间运行 Beat 不会提前判定失败；Worker 真正丢失时按上界失败。
- [ ] 停止 Worker、停止 Beat、制造积压和供应商失败时均有不泄露敏感内容的可定位信号。
- [ ] PostgreSQL 集成测试覆盖投递故障、重复消息、租约竞态和迟到响应。

## Out Of Scope

- 不改变 Redis 只作为 Celery Broker 的边界。
- 不增加供应商调用失败后的自动降级或静默重试。
