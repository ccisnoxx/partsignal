# 全项目功能、业务逻辑与 UI/UX 重新验收

## Goal

以专业测试和产品审查视角，对 PartSignal 全项目重新执行功能、业务逻辑、权限、可靠性、UI/UX、响应式和可访问性验收，找出可复现的产品与实现缺陷并形成发布风险结论。24 张业务表、全部操作列、13 个删除接口及其直接业务链路属于高风险重点，但不是本任务的范围上限。

## Background and Confirmed Facts

- 用户已在上线页面观察到多处表格/列表问题、操作列能力不完整，以及不同页面删除行为不符合预期。
- `frontend/tests/e2e/cross-page-visual-convergence.spec.ts:16-41` 已维护 24 张业务表清单，可作为本任务逐表验收基线。
- 正在进行的 `07-30-sitewide-table-list-guidelines` 负责表格信息层级、列宽、长文本、响应式与现有控件展示，并明确不改变权限、状态机和服务端能力；本任务补齐操作完整性、业务逻辑和删除安全，不重复建立表格视觉框架。
- 后端当前存在 13 个明确的 `DELETE` 路由，覆盖用户、产品、事实版本、内容任务、发布账号、发布记录、GEO 人工观测链、平台类型、平台 Prompt、平台、AI 渠道、请求 Header 和 AI 模型。
- 删除语义并不相同：部分对象允许无引用时硬删除，部分必须先停用或取消，发布与 GEO 历史受追加式规则保护，内容任务只允许清理尚未进入受保护下游历史的数据。测试不能把所有页面机械统一为同一种删除规则。
- 现有前端组件测试已覆盖部分内容任务、发布记录、GEO 观测、用户、事实版本、Prompt 和 AI 渠道删除路径，但产品、平台类型、发布账号、AI Header/模型等入口的覆盖不完整；现有 24 表 E2E 主要验证视觉与几何，不足以证明操作和删除安全。
- 现有后端集成测试覆盖多类服务和数据库删除守卫；本轮代码检索未发现覆盖全部删除路由认证、角色授权与 CSRF 的专门 HTTP 级矩阵，因此仍需运行时验证。
- `docs/deployed-full-functional-acceptance-plan.md` 已规定上线验收不得使用真实业务数据或实施生产破坏性测试，但其中关于内容任务删除资格的旧描述与当前 `contracts/database.md:279` 及服务实现不一致；本任务必须以当前合同和实现为准，并把文档漂移记录为待同步项。

## Requirements

### R1. 全项目功能与产品逻辑

1. 建立当前可访问路由、页面、角色、业务对象、主要用户任务和服务端接口的功能清单，不以旧文档中的“已通过”替代本轮证据。
2. 覆盖认证与会话、总览、用户与权限、平台/Prompt/发布账号配置、AI 渠道/Header/模型、产品与事实审核、内容任务/生成/自然化/人工录入/内容审核、发布候选/记录/证据/异常修复、GEO 主题/观测/纠错/洞察、文件和审计闭环。
3. 对每个核心业务状态机验证合法转换、非法转换、不可逆约束、并发 revision、重复提交、失败恢复、跨页面一致性和审计副作用。
4. 验证前端展示、OpenAPI、服务实现、数据库约束和产品文档一致；冲突项必须记录权威来源和产品影响，不能自行选择最容易通过的解释。

### R2. 角色、权限与数据边界

1. 覆盖未登录、工程师、管理员的导航、直达 URL、页面挂载、真实 HTTP 请求和会话失效。
2. 验证服务端是权限、状态转换和输入校验的最终权威；隐藏按钮、禁用控件或前端校验不能作为安全结论。
3. 覆盖 CSRF、输入边界、敏感字段脱敏、Markdown/错误安全显示、受限事实外发门禁，以及页面、响应、审计和浏览器存储中的秘密泄露。
4. 验证历史不可变与追加式规则：已批准事实/内容、发布事件、GEO 纠错链和审计不得被普通更新或不受控删除破坏。

### R3. 端到端业务闭环

1. 复用并校正 `docs/deployed-full-functional-acceptance-plan.md` 的 W0–W6：认证与配置、事实审核、内容任务与草稿、发布登记与核验、GEO 观测与纠错、发布异常与修复、恢复性与跨页面一致性。
2. 正向链路必须通过真实页面和真实服务端执行；测试替身只能位于项目已定义的外部服务边界，不得用前端固定成功响应代替业务实现。
3. 负向链路覆盖非法状态、权限不足、依赖禁用、旧 revision、重复提交、网络/服务失败和迟到响应，并验证不会产生伪成功或孤立数据。
4. 每条链路记录测试对象 ID、前置状态、状态变化、页面结果、网络结果、数据库或审计证据和清理/保留结论。

### R4. 全站表格与操作矩阵

1. 复用现有 24 表清单，逐表记录页面入口、数据对象、适用角色、行状态、操作列和详情入口。
2. 检查字段含义、排序、筛选、分页、加载、首次空数据、筛选无结果、失败、权限不足、响应式与返回后查询状态。
3. 对每个操作分别验证“应显示且可执行”“应显示但需解释为何不可执行”“不应显示且服务端仍拒绝”三种状态。
4. 操作列只呈现当前对象真正允许的动作；前端显示必须与服务端 `available_actions`、角色权限和对象状态一致，不能自行猜测或补造能力。

### R5. 删除产品逻辑

1. 为 13 个删除接口建立对象级合同，明确删除资格、角色、状态前置、关联数据、历史保留、审计、副作用、错误码和恢复路径。
2. 区分停用、取消、移除、归档、软删除、硬删除和禁止删除；界面使用用户能理解的业务语言，确认正文说明不可恢复性与真实影响。
3. 删除入口不得成为默认主操作；危险操作进入二次确认，确认对象、影响范围和最终按钮文案必须明确。
4. 删除成功后列表、详情、分页总数、工作台指标和关联查询保持一致；失败时保留对象和必要上下文，并提供可理解的原因。

### R6. 删除安全与数据完整性

1. 验证未登录、工程师、管理员及对象状态边界；前端隐藏按钮不作为安全结论，必须验证服务端真实拒绝。
2. 验证 CSRF、直接请求、旧页面/旧状态、重复点击、请求重放、并发状态变化和不存在对象等场景。
3. 验证数据库外键、删除守卫、受保护历史、附件清理调度和审计记录符合当前合同；任何失败不得留下部分删除或伪成功状态。
4. 页面、响应、审计、控制台和测试证据不得泄露密码、Cookie、Token、API Key、敏感 Header 或完整认证状态。
5. 上述破坏性场景使用可重建的开发测试数据真实执行，不以 mock 成功或只检查按钮替代服务端和数据库结果。

### R7. 全项目 UI/UX 与可访问性

1. 对全部页面检查信息架构、视觉层级、术语、控件一致性、表单校验、加载/空/失败/权限状态、操作反馈、错误恢复和用户掌控。
2. 重点检查操作列宽度、固定列遮挡、菜单可达性、危险层级、按钮命名、确认弹窗、成功反馈和结构化错误展示。
3. 在桌面、移动端、真实 200% 缩放、浅色/深色/跟随系统、仅键盘和 reduced-motion 场景验证关键操作可见、可达、可取消、可恢复。
4. 不把“能点击”当作通过；写操作完成后必须验证服务端结果、页面状态和审计副作用。

### R8. 缺陷与后续修复输入

1. 每个缺陷记录唯一 ID、类型、严重程度、角色、前置数据、最短复现步骤、期望/实际结果、HTTP/业务错误码、证据和影响范围。
2. 需求歧义单独列为产品决策项，不把不确定预期写成实现缺陷。
3. 本任务完成缺陷确认、共同根因归组、优先级和建议修复边界；不在测试过程中修改业务代码。
4. 基线冻结后，为确认缺陷另行建立修复任务；修复任务负责针对性回归和同类页面检查。

## Acceptance Criteria

- [ ] 形成当前全项目功能、路由、角色、状态机、业务对象和接口清单，并标明本轮实际执行状态。
- [ ] 认证、配置、事实、内容、发布、GEO、文件与审计的适用端到端链路均有 PASS/FAIL/BLOCKED/NOT_APPLICABLE 和证据。
- [ ] 未登录、工程师、管理员的页面和服务端权限矩阵完成；秘密、受限事实、历史不可变和输入安全边界有明确结论。
- [ ] 核心状态机的合法、非法、重复、并发、失败恢复和跨页面一致性均有验证结果。
- [ ] 形成可追踪到 24 张表、页面入口、数据对象、角色、行状态和接口的测试矩阵。
- [ ] 13 个删除接口均有删除资格、权限、状态、关联数据、确认文案、成功副作用、失败恢复和审计的明确产品合同。
- [ ] 所有操作列均完成允许显示/执行、禁止执行和服务端绕过验证，不以按钮隐藏代替权限测试。
- [ ] 所有删除入口均有正常、异常、越权、CSRF、状态冲突、重复操作、并发变化、关联影响和历史保护的测试证据；不适用项需说明合同依据。
- [ ] 表格与操作列在桌面、移动端、真实 200% 缩放和键盘场景可读、可达且不会遮挡关键操作。
- [ ] 全项目页面完成 UI/UX、浅深主题、响应式、键盘、焦点、对比度和关键异常状态验收；未覆盖项明确标记。
- [ ] 每个确认缺陷都有唯一记录、严重程度、可复现证据和明确预期；产品歧义不混入缺陷统计。
- [ ] P0/P1 缺陷修复并完成回归前，不给出可安全发布结论。
- [ ] 输出测试报告，明确已覆盖、未覆盖、PASS/FAIL/BLOCKED、缺陷分布、阻断项和残余风险。
- [ ] 输出按共同根因和优先级拆分的后续修复任务建议，但本任务不包含修复提交。
- [ ] 记录与当前 OpenAPI、数据库合同和实现不一致的权威测试/设计文档，并给出后续同步建议；本任务不直接修正文档。

## Out of Scope

- 规划阶段不修改业务代码、不执行测试写操作。
- 整个任务不修复发现的业务代码缺陷；修复和修复后回归由后续任务负责。
- 不把生产环境保护规则作为开发环境测试限制；生产部署验收仍由独立计划负责。
- 不实施容量压测、漏洞利用或持续高频请求；这些不是本轮全功能验收。
- 不为了界面一致而改变已经证实合理的对象级删除语义。

## Key Decisions

- 本任务以开发环境为目标，允许对可重建测试数据执行完整删除矩阵；安全性仍作为被测产品属性，不作为限制测试深度的理由。
- 本任务只测试和出报告，先冻结缺陷基线；不边测边改，修复另行立项。
- 本任务覆盖全项目功能、业务逻辑、权限、可靠性和 UI/UX；24 表、全部操作列与 13 个删除接口作为重点风险专项，不作为范围上限。
