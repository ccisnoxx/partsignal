# 重新设计发布管理业务流程

## 目标

从 PartSignal 的完整业务闭环出发，重新定义“发布管理”的业务职责、对象、状态和用户流程，使已批准内容能够清晰地完成外部人工发布、结果登记和首次核验，并让后续 GEO 观测、页面异常与内容修复各自回到唯一责任边界。

本任务不以修补当前发布管理页、增加删除提示或调整既有 Tab 为出发点。当前页面、接口、状态枚举和数据表都只是需要审查的现状；只有符合重新确认业务流程的部分才保留，冲突部分应被替换或删除。

## 业务流程基线

项目权威方案定义的主闭环是：

```text
真实且统一的产品事实
→ 已批准的差异化平台内容
→ 外部人工发布
→ 公开结果登记与首次核验
→ GEO 观测
→ 识别失败环节
→ 创建新的内容任务或修复任务
```

发布管理位于“已批准内容”与“可供 GEO 观测的公开文章”之间，必须回答四个问题：

1. 哪些已批准内容现在需要发布？
2. 某次人工发布工作进行到哪一步，下一步是什么？
3. 外部平台最终产生了什么可追溯的公开结果？
4. 首次核验是否完成，何时可以把文章交给 GEO 观测与后续运营？

## 已确认业务不变量

- 只有绑定有效已批准事实的 `APPROVED ContentVersion` 才能进入发布流程：`docs/GEO多平台内容运营系统方案设计.md:174-192`。
- 内容任务已经锁定一个具体平台；发布账号必须属于该平台，一次人工发布只选择一个账号：`docs/GEO多平台内容运营系统方案设计.md:257-265`。
- 实际外发内容必须与批准内容一致；发生实质正文修改时必须先创建新内容版本并重新审核：`docs/GEO多平台内容运营系统方案设计.md:603-615`。
- 外部发布成功后必须保存实际标题、最终 URL、发布时间、账号、内容版本、说明和可选证据，且平台、URL 和内容版本不能被静默覆盖：`docs/GEO多平台内容运营系统方案设计.md:393-416`。
- GEO 观测只消费具有公开链接的真实发布结果，不拥有或覆盖文章 URL、标题、平台和内容版本：`docs/GEO多平台内容运营系统方案设计.md:266-273`、`contracts/database.md:426-427`。
- 系统不得猜测未知状态、伪造发布成功、用前端隐藏代替服务端状态与权限校验，或为测试数据增加成功绕过。
- PostgreSQL 是唯一业务状态来源；关键状态转换、历史、权限、并发与审计必须由服务端最终控制。

## 已确认产品决策

- 首次核验成功是人工发布流程的完成边界。
- 完成后形成只读公开结果，后续页面可访问性、内容变化和运营异常不再回写或重新打开原发布工作。
- 公开后的问题进入独立的问题处理流程；需要修复内容时创建新的内容任务，完成审核后再开始新的发布工作。
- 当前处于开发阶段，新设计可以替换不合理的旧状态机、接口和页面，不为内部旧结构保留兼容包装或双写。
- 现有开发与预发布业务数据按测试数据处理，可以在新设计落地时重置并按新流程重新生成；不为旧混合状态编写猜测式兼容迁移。
- 首次核验失败仍属于未完成的发布工作，必须继续出现在待处理队列；用户可以修正外部页面后重复核验，或填写原因显式关闭该发布工作。
- 首次核验失败不会创建发布后问题；只有已经首次核验成功的公开结果后来出现问题，才进入独立问题处理流程。

## 本轮设计提案（待最终评审确认）

- 单条发布工作、核验历史、已发布成果和内容问题不提供物理删除入口；误操作、平台拒绝和无法继续通过带原因关闭表达。开发环境整体重置是部署级数据处理，不是日常业务删除能力。
- 显式关闭发布工作同时把来源内容任务置为 `CANCELLED`，避免同一条已放弃内容立即重新出现在待发布候选；如需再次发布，应创建新的内容任务和发布工作。
- 一份已批准内容版本只创建一条发布工作；同一工作可以重复核验，但关闭后不自动重开或生成重试记录。

## 当前模型的结构性问题

### 1. 一个状态字段承担了四类不同业务事实

当前 `PublicationRecord.status` 同时表达：

- 人工发布工作：`PENDING_MANUAL_PUBLISH`、`PLATFORM_REVIEW`；
- 公开结果：`PUBLISHED`；
- 首次核验结论：`VERIFIED`、`VERIFICATION_FAILED`；
- 公开后的页面变化：`REMOVED`。

这些状态不属于同一个生命周期。发布工作可以结束，公开结果应成为不可变历史，页面健康可以反复变化，异常处置也有独立的打开与解决过程。把它们串成一个当前状态，使“当前是什么”和“历史发生过什么”互相覆盖。

### 2. 页面按数据库对象组织，而不是按运营任务组织

当前 `/publications` 并列展示“待发布候选、发布记录、发布关注事项”，但三者分别是派生输入、混合生命周期记录和异常待办。用户必须理解内部模型，才能判断去哪个列表、为什么同一文章同时出现、下一步应该在哪里完成。

### 3. 发布完成边界不清

现有内容任务在首次 `VERIFIED` 后进入 `COMPLETED`，但同一发布记录随后仍可进入 `REMOVED` 或 `VERIFICATION_FAILED`，并继续留在发布工作台。系统没有清楚区分“发布任务已经完成”与“已发布文章后来出现运营问题”。

### 4. 删除争议是模型混乱的结果

用户看到 `VERIFICATION_FAILED` 时会自然理解为“这次发布失败”，而现有模型实际表达“曾经公开，后来核验失败”。删除入口是否出现只是表象；根因是失败发生在哪个阶段、失败关闭什么工作、是否产生公开结果没有被独立表达。

## 重新设计要求

### R1. 先定义业务对象，再定义页面

- 从业务事件和责任边界重新识别最小对象，不默认沿用 `PublicationRecord`、`PublicationAttention` 或当前状态枚举。
- 至少必须独立表达“待发布输入 / 人工发布工作”“实际公开结果”“核验记录或页面状态”“异常处置”中的真实不同所有者；如果两个概念能够由同一权威事实无歧义派生，则不重复建模。
- 每个长期业务事实只能有一个权威所有者，派生列表不得成为第二份可编辑状态。

### R2. 发布流程必须有明确起点和终点

- 起点是一个具体平台上的已批准内容进入人工发布工作。
- 流程必须明确覆盖：选择账号与栏目、外部人工操作、平台处理中/拒绝、公开结果登记、首次核验。
- 每个阶段必须有唯一下一步、明确失败出口和可观察完成条件。
- 首次核验成功后发布工作完成；已完成工作不再伪装成待办，公开结果进入只读历史并成为 GEO 观测候选。
- 首次核验失败只追加核验事实并把发布工作标记为需要处理，不关闭工作；后续复核成功或用户填写原因显式关闭，二者必须保留不同结果。
- 显式关闭是终止本次内容任务的业务命令，不等同于删除记录、隐藏失败或自动生成一次重试。

### R3. 区分公开前失败与公开后问题

- 公开前被平台拒绝、用户取消或登记错误，不得与已经产生真实 URL 的页面失效混为一个“失败”状态。
- 已经公开的文章后来下线、内容不符或不可访问，必须作为公开结果的后续运营事件或问题处理，不能倒写发布工作未完成。
- 是否允许同平台重新发布，必须根据明确的业务身份和真实公开事实决定，不根据模糊当前状态猜测。

### R4. GEO 与修复回流边界

- GEO 只读取符合观测资格的公开结果，不修改发布工作或公开历史。
- 首次核验成功后的页面问题或内容效果问题进入独立的问题处理流程，并按需要创建新的内容任务；原发布工作保持完成，修复任务不得直接覆盖原内容、原公开结果或原观测。
- 问题是否已处理、修复任务是否已创建、修复内容是否重新发布是不同事实，不得用一个布尔值或状态互相代替。

### R5. 页面按用户工作组织

- 页面首先展示“现在需要处理什么”，其次提供已完成发布结果与历史查询；不得要求用户理解数据库表关系。
- 每条待办显示来源、当前阶段、唯一推荐动作、阻断原因和最近业务事件。
- 已完成、失败关闭和后续异常必须有清晰归属，不在多个并列入口重复承担主操作。
- 统计只服务于运营判断，不从分页列表前端重算，也不把状态数量堆叠当作业务流程。

### R6. 允许真正替换旧设计

- 可以修改 OpenAPI、数据库合同、表结构、状态枚举、服务边界和页面信息架构；本任务不要求保留冲突的内部 API 或旧前端结构。
- 新数据库结构必须支持全新环境直接迁移到 head；现有开发/预发布测试数据允许整体重置，不迁移旧发布、关注事项和依赖它们的 GEO 数据。
- 迁移后删除旧状态机、重复投影和失效页面路径，不保留无业务价值的兼容包装、双写或第二套状态源。

## 验收标准草案

- [ ] AC1：从一个已批准内容开始，用户可以沿单一清晰路径完成账号选择、外部发布、结果登记和首次核验。
- [ ] AC2：公开前拒绝/取消、成功公开、首次核验失败、显式关闭、公开后页面失效分别具有独立且不歧义的业务含义和后续动作。
- [ ] AC3：发布工作完成后不再出现在待处理队列；实际公开结果作为可追溯历史进入 GEO 候选。
- [ ] AC4：页面异常或内容问题不会改写已完成发布事实，而是形成独立问题处理与修复回流。
- [ ] AC5：用户无需理解 `PublicationRecord`、状态事件或关注事项表，即可判断每条记录为什么出现、当前由谁处理、下一步是什么。
- [ ] AC6：所有可执行动作、阻断原因、权限和并发资格由服务端投影并最终校验，前端不复制业务规则。
- [ ] AC7：新结构支持全新环境迁移与种子数据重建；重置旧开发数据后不存在旧状态机双写、猜测映射或兼容读路径。
- [ ] AC8：权威业务文档、OpenAPI、数据库合同、后端服务、前端生成类型、页面和测试描述同一套流程。
- [ ] AC9：自动化验证覆盖正常发布、平台处理中、公开前拒绝、首次核验失败、公开后失效、问题解决、修复任务及重新发布闭环。
- [ ] AC10：首次核验失败可以重复复核或修正登记结果，失败历史始终保留；显式关闭后来源内容任务取消，原候选不再自动回到待办。

## 范围外

- 不实现跨平台自动发布、页面抓取或 CDP/RPA。
- 不重新设计事实维护、内容生成与内容审核流程；只调整它们与发布流程的输入输出边界。
- 不重做 GEO 指标公式；只明确 GEO 如何消费公开结果、如何触发优化回流。
- 不新增工作流引擎、事件总线、插件系统、通用状态机框架或为未来自动化预留的空抽象。
- 不为旧内部结构保留未经业务需要证明的兼容层。

## 现有开发数据处理

- 当前开发库有 83 条发布记录和 382 条状态事件；83 条均曾进入 `PUBLISHED` 与 `VERIFIED`，其中 50 条当前为 `REMOVED`、33 条为 `VERIFIED`。
- 50 条旧 `PublicationAttention` 均已解决；66 条发布记录被 132 条 GEO 逐篇观测关系引用，36 条发布记录还被旧 GEO 引用关系引用。
- 这些数据按旧混合状态机生成，视为开发/预发布测试数据；实施时采用明确的环境重置和新种子/验收流程，不尝试拆分或映射为新业务对象。
