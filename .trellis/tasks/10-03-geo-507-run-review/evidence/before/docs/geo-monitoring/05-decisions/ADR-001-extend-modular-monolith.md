# ADR-001：在现有模块化单体内扩展 GEO 监测

- 状态：Accepted
- 日期：2026-10-01
- 接受日期：2026-10-01
- 接受依据：用户在本会话明确接受本 ADR 及 GEO-002 评审修订。
- 适用范围：PartSignal GEO 监测核心版在现有前后端模块化单体中的扩展，以及事实、文件、身份、凭据和 Browser 执行服务的集成边界。

## 背景

PartSignal 已经以 FastAPI/SQLAlchemy/PostgreSQL 构成模块化单体，并在产品事实、内容、审核、发布、人工 GEO 和审计之间存在大量事务一致性关系。GEO 监测将增加计划、运行、分析、机会和复测，但仍需要直接复用这些领域。

## 决策

GEO 核心版继续作为现有后端和前端中的模块化子域实现，不拆微服务，不引入独立业务数据库或事件总线。

PostgreSQL 继续是业务状态唯一来源；Redis 只承载 Celery 消息；对象存储保存大文件。

## 替代方案

1. 独立 GEO 微服务；
2. 使用 MongoDB 保存回答；
3. 使用第三方 SaaS 作为核心监测数据源。

## 原因

- 跨域事务和稳定 ID 关系密集；
- 当前团队和部署规模不需要分布式复杂度；
- PostgreSQL 足以支持核心查询和 JSONB 快照；
- 内部自用强调数据所有权和可审计性；
- 可通过明确模块、Worker queue 和独立 browser service 控制边界。

## 后果

正面：

- 复用权限、审计、凭据、对象存储和部署；
- 事务和迁移简单；
- Codex 可按纵向切片实现。

负面：

- 主仓库和数据库继续增长；
- 需要严格模块所有权和查询性能治理；
- Browser runtime 不能直接塞入普通单体容器，因此允许独立执行服务但不拥有业务状态。

## 重新评估条件

- 单个数据库无法满足容量/隔离目标；
- Browser Collector 需要独立安全域且现有 API 无法承载；
- 团队和部署规模证明服务独立性收益高于分布式成本。

## GEO-002 评审修订（已接受）

- 接受结论：用户接受模块化单体方向及以下评审修订，作为后续 GEO 合同与实施任务的架构依据。
- GEO 子域拥有计划、运行、分析、复核及其指标选择规则；事实、发布、文件、身份与凭据继续由既有权威模块拥有。复用基础设施不等于复用内容生成的业务输出模型。
- 新证据引用必须接入 FileRecord 的关联资格、行锁及清理判断；事实版本引用必须接入删除阻断或经批准的完整历史快照方案。不得只新增 GEO 外键而遗漏既有生命周期命令。
- Browser 服务只执行受控采集，不拥有计划、状态转换、授权或业务数据库；专用队列、功能开关和隔离部署是后续实施项。
