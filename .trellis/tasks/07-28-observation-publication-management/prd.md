# 完善观测与发布管理流程

## Goal

让产品测试中的观测登记、观测更正、证据管理和发布管理符合真实业务语义，同时保留服务端权威校验、历史审计和附件生命周期的一致性。

## Background

- 本任务包含两个可独立验收的交付：
  - `07-28-observation-evidence-management`：观测事实、证据附件和记录处置。
  - `07-28-publication-management`：发布管理导航、列表、关注事项和记录处置。
- 当前人工观测把 `discovered`、`mentioned`、`recommendation_status`、`cited`、`accuracy` 建模为逐发布内容事实，并强制累计阶段关系（`contracts/database.md:131-141,171-179`）。
- 当前观测、更正、发布记录、发布状态事件和关注事项属于追加式历史；数据库和 API 均没有观测或发布记录删除能力（`contracts/database.md:49-63,97-105,131-141`）。
- “发布需关注”不是独立发布入口，而是 `REMOVED` 或 `VERIFICATION_FAILED` 产生的 OPEN 异常待办（`.trellis/spec/backend/publication-workbench-guidelines.md:24-35`）。
- Playwright CLI 已实际打开本地前端；登录 500 已定位为当前 Vite 进程仍使用默认代理 8000、实际后端运行在 18000 的启动参数不一致，不是账号或业务接口失败。

## Requirements

- 观测事实必须改为用户确认后的独立业务含义，不保留无产品价值的阶段字段或前端第二套推断。
- 新建和更正观测不得以重复上传截图作为提交前提；附件关系和清理行为必须有唯一服务端所有者。
- 观测与发布记录按已确认的业务事实成熟度执行受约束删除，不能用前端隐藏或裸 DELETE 绕过数据库门禁。
- 导航“人工发布”改为“发布管理”，并完善发布记录、发布关注事项和服务端可用操作的呈现。
- 发布管理必须解释“发布需关注”的触发条件并提供可发现的处理入口。
- 最终使用真实 API 数据和 Playwright CLI 验证观测、发布记录及关注事项流程；不得用路由拦截伪造成功。

## Acceptance Criteria

- [x] 两个子任务均通过各自验收，且跨页面命名、状态、操作和附件行为一致。
- [x] `contracts/openapi.yaml`、`contracts/database.md`、后端实现、生成的前端类型和页面行为保持一致。
- [x] 删除或处置记录后，不存在失去引用但永久遗留的证据对象，也不破坏依法保留的业务历史。
- [x] Playwright CLI 使用显式正确的 API 代理目标完成真实登录及代表性流程，产品代码不增加本地端口 fallback。

## Out of Scope

- 不把“所有列表都应有删除功能”扩展为全站批量改造；只处理本任务明确涉及且经契约允许的观测、发布记录。
- 不新增统计表、缓存状态、第二套附件系统或前端业务状态机。
- 不恢复自动发布能力；发布仍是人工登记与后续状态管理。

## Key Decisions

- 采用“按业务事实成熟度受约束删除”：
  - 人工观测属于可录错、可更正的运营输入，删除时物理删除整条更正链，避免旧版本重新成为当前记录。
  - 发布记录只有在从未出现 `PUBLISHED` 或 `VERIFIED` 事件、且不存在 GEO 观测、关注事项、修复任务等下游引用时才允许物理删除。
  - 曾真实发布的记录继续使用“标记已移除”及异常处理流程；不能物理删除，也不能从历史发布指标中抹除。
  - 删除聚合记录后，只有失去全部真实外键引用的附件文件才进入对象存储清理；审计日志永久保留。

## Constraints

- PostgreSQL 是业务状态唯一来源，服务端是状态转换、权限和输入校验的最终权威。
- 已批准事实、内容、发布事件和 GEO 观测历史不得在未明确批准契约变更时原地修改。
- 复杂任务必须在阻塞产品决策清空后补齐 `design.md` 和 `implement.md`，经用户审阅后才能进入实现。
