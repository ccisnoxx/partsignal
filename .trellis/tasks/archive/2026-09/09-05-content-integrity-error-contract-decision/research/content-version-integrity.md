### 3. 领域分类与公共合同冻结结论

推荐的四类结果如下：

1. `uq_content_versions_source_job_id`：只在 worker 中识别精确 diagnostics；可验证 winner 时 **replay existing ContentVersion**，不是 HTTP 409，也不产生第二次 provider call/dispatch。没有可验证 winner 时 **explicit Job FAILED/GENERATION_FAILED**，不猜测。
2. `uq_content_versions_task_id`：**unknown**。锁定 task 后的 `max(version)+1` 已足以消除合法 race；唯一冲突暴露的是 invariant/owner 异常，不属于 revision conflict。
3. `uq_content_versions_one_pending_per_task`：**map** 到新领域错误 `CONTENT_REVIEW_ALREADY_PENDING`，仅 exact `23505 + constraint_name`；409、准确中文 message、空 details、统一 request ID，前端保留本地输入并显式 reload，不自动 replay。
4. `uq_content_versions_one_approved_per_task`：**unknown**。既有 approved 在正常 approve 流程中是可 supersede 的，不存在一个无歧义的 replay winner；唯一冲突表示状态无法证明，默认 500。

公共 envelope 仍是 `{error:{code,message,details,request_id}}`，且 response `X-Request-ID` 继续由 runtime metadata 注入。`CONTENT_REVIEW_ALREADY_PENDING` 的 409 已由 `submitContentVersion` route 声明，故本决定不要求 OpenAPI response/status、runtime metadata 或 `frontend/src/shared/api/generated/schema.d.ts` 结构变化；ErrorDetail.code 当前是开放 string（父研究 `api-frontend-impact.md:21-23,42`），不新增 enum。仍需在后续 implementation 中同步稳定 backend specs、Frontend V2 Error Contract 文字和前端 code-aware projection；若产品要求把 code 纳入 OpenAPI enum，必须另开更窄合同变更并重新生成 client。

`REVISION_CONFLICT` 只保留真实 `expected_revision` stale（例如 `review.py:356-357`、`content_production.py:906-909`）。不把四项唯一性错误统一转成该 code；不恢复全局 registry/mapper framework/repository/第二套错误类型；不解析数据库消息。已完成 Humanization 的 `uq_generation_jobs_idempotency_key`→同 identity replay/异 identity `IDEMPOTENCY_CONFLICT`、`uq_generation_jobs_active_humanization_source`→`HUMANIZATION_ALREADY_ACTIVE`（`content_production.py:353-365,576-588,715-729`）保持不变。

## Caveats / Not Found

- 当前运行时模型将 `uq_content_versions_task_id` / `source_job_id` 留给 naming convention 生成名称；本审计没有执行数据库连接查询 `pg_constraint`/`pg_indexes`，因此真实部署 catalog 仍应由 implementation Task 的 PostgreSQL test 直接断言。历史迁移和 model 定义一致，但不可用名称猜测替代 catalog 证据。
- `uq_content_versions_one_approved_per_task` 的历史迁移创建位置在父任务研究和 current model 可确认，但本次没有修改/重放 migration，也没有读取生产数据；若某环境 schema 未升级到 `0035`，应先按迁移状态失败，不添加兼容 fallback。
- `content_versions.source_job_id` 是 nullable，PostgreSQL UNIQUE 允许多个 NULL；只讨论非空 source job duplicate。`task_id/version` 的 partial indexes 不覆盖 DRAFT/CHANGES_REQUESTED 等状态以外的 version uniqueness；不能把 partial index 语义推断到普通 `(task_id, version)` constraint。
- pending 冲突新 code 是产品语义建议而非已落地公共合同；本 research 不修改 `contracts/openapi.yaml`、稳定 specs、frontend、业务代码或测试。若产品拒绝新增 code，pending 必须降级为 unknown 500，并相应删除后续 frontend code-aware Task，而不是改用 `REVISION_CONFLICT`。
- worker replay 只允许在 rollback 后由相同 `source_job_id` 查询到可验证 winner；不能依据错误文本、`version` 最大值或 task pointer 反推 winner。worker 不使用 HTTP request policy、不会返回 ErrorEnvelope，Job FAILED/重放是其独立失败合同。
- 本审计没有运行测试，符合父任务 planning-only 边界；未执行 `task.py start`、Git、数据库写入、生产操作或浏览器会话。上述 required commands 是后续 implementation Task 的建议，不是本研究已通过的验证。
