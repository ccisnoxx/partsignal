# AI 配置删除并发一致性修复

## 1. 目标

修复 AI 渠道和 AI Header 同目标并发删除时两个请求都返回 `204`、并写入两条成功审计的问题。修复后，服务端必须以 PostgreSQL 中的目标行为并发权威：只有取得并删除目标的请求成功，等待方在锁释放后确认目标不存在并返回 `404`。

## 2. 已确认事实

- 第二轮全项目回归将问题登记为 `PS-QA2-DELETE-001`，严重程度 P2；稳定复现的实际结果是 AI 渠道与 Header 均为 `204/204` 且各有两条成功审计，其余 11 个 DELETE 为 `204/404` 且只有一条成功审计。
- `contracts/openapi.yaml:926-970` 与 `1108-1140` 已同时声明删除成功 `204` 和目标不存在 `404`，本任务不改变公开 API。
- `backend/app/services/ai_configuration.py:390` 的渠道删除先用 `db.get` 读取，再追加审计并删除，没有锁定目标行。
- `backend/app/services/ai_configuration.py:511` 的 Header 删除先用 `db.get` 读取 Header，只锁父渠道；等待后仍可继续处理过期 Header 对象并重复失效渠道/模型。
- `backend/app/services/ai_configuration.py:326` 的模型配置锁和 579 行的模型删除已使用 `SELECT ... FOR UPDATE`，本轮并发结果为 `204/404`，可作为现有正确模式。
- HTTP 路由已为每个请求注入独立数据库会话；真实缺陷只需在服务层权威写入边界修复，不需要前端防重或兼容分支。

## 3. 范围内需求

### R1. 渠道删除的单一成功者

- `delete_ai_channel` 必须在追加成功审计和删除前用 PostgreSQL 行锁读取目标渠道。
- 等待方在前一事务提交删除后必须得到“AI 渠道不存在”的既有 `404`，不得追加成功审计或再次执行删除副作用。
- 成功请求继续按现有关系和外键合同删除渠道、Header、模型，并保留生成作业快照及可空外键语义。

### R2. Header 删除的单一成功者

- `delete_ai_channel_header` 必须锁定目标 Header；只有仍存在的 Header 才能继续锁父渠道、删除目标并调用 `invalidate_channel_models`。
- 等待方在目标已删除后必须返回既有“渠道 Header 不存在”`404`，不得再次增加渠道/模型 revision、重置状态或追加成功审计。
- 成功请求仍按现有行为停用渠道和全部子模型，将模型测试状态重置为 `UNTESTED`，不改变业务副作用。

### R3. 永久并发回归测试

- 在 `backend/tests/integration/test_ai_channel_management.py` 使用真实 PostgreSQL、真实 FastAPI 路径、两个独立请求/数据库会话和同步起跑验证两个删除入口。
- 每个入口必须断言状态码排序后为 `[204, 404]`、目标最终不存在、成功审计恰好一条。
- Header 用例还必须断言渠道及子模型只失效一次，revision 只增加一次；渠道用例必须断言子 Header/模型按现有级联语义消失。
- 测试必须有有界等待并依赖 PostgreSQL 行锁，不能用 SQLite、固定成功响应或前端按钮状态替代。

### R4. 稳定规范同步

- 在 `.trellis/spec/backend/ai-configuration-guidelines.md` 记录 AI 配置删除的目标行锁、单一成功审计和 `204/404` 并发不变量。
- OpenAPI、数据库 Schema、迁移和前端生成类型不变；若实施中发现必须修改这些合同，应返回规划阶段重新评审。

## 4. 范围外

- 不处理 `PS-QA-201`～`203`、状态动作投影、24 表门禁、favicon、Timeline 或共享对象存储问题。
- 不修改删除确认文案、焦点恢复、React Query 缓存或其他前端代码。
- 不重构其余 11 个 DELETE 接口，也不建立通用删除框架、锁管理器或兼容层。
- AI 模型删除只作为正确对照和不回归对象，不改变其公开行为。
- 不新增数据库列、约束、迁移、错误码或 revision 请求参数。

## 5. 验收标准

- [x] AC1：同一 AI 渠道的两个并发 DELETE 稳定得到一个 `204` 和一个 `404`，数据库中渠道及其 Header/模型不存在。
- [x] AC2：渠道并发删除只产生一条 `ai_channel.deleted` 成功审计，落后请求不产生第二条成功记录。
- [x] AC3：同一 AI Header 的两个并发 DELETE 稳定得到一个 `204` 和一个 `404`，目标 Header 不存在。
- [x] AC4：Header 并发删除只产生一条 `ai_channel_header.deleted` 成功审计，渠道和全部子模型的失效状态及 revision 只变化一次。
- [x] AC5：顺序首次删除/重复删除、权限、CSRF、404、渠道级联和 Header 删除副作用保持现有合同；AI 模型删除不回归。
- [x] AC6：永久 PostgreSQL 集成测试覆盖两个原缺陷路径，目标测试、完整集成、合同、lint 与类型检查均通过且隔离数据库已清理。
- [x] AC7：AI 配置后端规范已补充并发删除不变量；产品代码和测试之外没有前端、OpenAPI、数据库合同、迁移或部署改动。

## 6. 约束与风险

- PostgreSQL 是唯一能证明本缺陷的测试边界；SQLite 或单会话测试不计验收证据。
- 并发测试复用第二轮探针已经稳定使用的独立 `TestClient`、独立会话和 `Barrier` 起跑模式，避免引入生产测试钩子。
- 修复必须发生在服务端共同写入边界，不能依赖前端禁用按钮或请求去重。
- 本任务没有未决产品、兼容或数据迁移决策。
