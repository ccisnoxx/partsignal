# Research: Publication/GEO 错误合同与前端影响审计

- Query: 审计 publication/GEO operation、错误 schema、运行时响应元数据、生成客户端、前端消费者及测试，评估 `REVISION_CONFLICT`、`REPAIR_TASK_EXISTS` 与其他 409/500 wire/status/code 决策的影响。
- Scope: mixed（仓库合同、后端运行时、前端生产代码/测试、Frontend V2 文档与稳定 spec）
- Date: 2026-09-14

## Findings

### 1. 当前冻结的 wire/status 基线

1. **错误 wire 只有一个闭合信封。** `contracts/openapi.yaml:4192-4206` 定义闭合的 `ErrorEnvelope -> ErrorDetail`：必填 `code`、`message`、`details`、`request_id`，其中 `code` 是普通 string，`details` 是可扩展 object；`components.responses.ErrorResponse` 被所有业务错误状态复用。后端运行时的对应 owner 是 `backend/app/errors.py:15-53`：调用方明确列出状态，`AppError` 按原始 code/status/details 生成同一信封。
2. **publication operation 已显式列出 409，但未列 500。** 例如 work detail/workspace 与 preparation 等 command 的 OpenAPI response 分别在 `contracts/openapi.yaml:2862-2894`、`:2895-2921`、`:2922-2967`；所有已审计 publication operation 的业务错误状态都引用 `ErrorResponse`。issue operation 也保持同样模式（open issue 例见 `contracts/openapi.yaml:3620-3667`）。
3. **GEO operation 的 409 范围按资源语义冻结。** Observation list/list-items 显式有 409，candidate list 没有 409，而 create observation、detail、correction context/correction command 等按需列出 409（`contracts/openapi.yaml:3668-3752`、`:3753-3785`；detail/correction operation 从 `:3786` 起）。因此不能把“所有 GEO endpoint 统一加 409/500”当作无害合同扩展。
4. **请求 ID 是跨切面 metadata，不是业务错误 code。** `backend/app/main.py:153-245` 在运行时给每个 operation 合并可选 `X-Request-ID` 输入、400 `ErrorResponse` 和响应 `X-Request-ID`；`:261-295` 负责生成/回显 request ID、非法输入返回 400。该合并不改变 route owner 的业务状态集合。
5. **500 不在当前 public contract。** `backend/tests/unit/test_contract.py:293-315` 要求 162 个 operation 精确匹配状态集合、无 `500`、无 `default`/`4XX`，所有非成功响应均是 `ErrorResponse`；`backend/tests/unit/test_runtime_response_metadata.py:639-682` 要求 162 个 operation、1024 个响应都有 request-ID 元数据，且无 `default`/`4XX`；`:778-797` 进一步断言 Wave 3 无任何 5xx。`.trellis/spec/backend/error-handling.md:282-285` 还明确未知 `IntegrityError` 应落到 FastAPI/Starlette 默认 500，默认 500 body/code/header/media type 不是冻结合同，禁止为了它新增 OpenAPI 500、生成客户端分支或前端稳定 code。

### 4. generated client 与 runtime metadata 的具体影响

- OpenAPI 生成结果当前直接反映 `ErrorDetail.code: string` 和 operation 的状态 map；例如 `frontend/src/shared/api/generated/schema.d.ts:2106-2117` 没有 `REVISION_CONFLICT`/`REPAIR_TASK_EXISTS` 字面量 union，publication operation 的 409 response 由各 operation 映射到 `components.responses.ErrorResponse`（路径 operation 定义从 `:1499`、`:1534`、`:1620` 等可见）。因此“新增一个稳定 code 名称”是 wire value 兼容变更，不应手改 generated client；只有 status、ErrorDetail required/shape 或 details 子结构改变才需重新生成并核对全量 consumers。
- `backend/tests/unit/test_runtime_response_metadata.py:639-682` 的检查证明请求 ID 参数、响应 header、400 envelope 是全局不变量；`:685-695` 的 raw/stripped comparator 证明 metadata merge 不得篡改业务 route status；`:698-716` 还保证 merge 中途失败不缓存 partial schema。任何 status 变化都必须同时更新静态合同、raw route owner、运行时 Wave 期望和 comparator；code-only 决策不应触碰 runtime metadata。
- 运行时 status 计数当前 Wave 3 为成功 `200:34, 201:6, 204:3`，错误 `401:43, 403:43, 404:32, 409:37, 422:39`（`backend/tests/unit/test_runtime_response_metadata.py:799-840`）。若 T5 只是明确 `REPAIR_TASK_EXISTS`/`PUBLICATION_CONTEXT_INCOMPLETE` 的 code，计数不变；若新增/删除某 operation 的 409，须重新审计该计数及 `WAVE_3_EXPECTED_STATUSES`（`:444-502`），并同步 `backend/tests/unit/test_contract.py` 的精确状态断言。

### 5. 前端 production consumer 现状

#### Publication

- `frontend/src/domains/publication/publication.api.ts:36-45` 的 `PublicationRequestError` 保存 HTTP status 与生成的 `ErrorDetail`；`:437-487` 的 `mapPublicationError`/`publicationRequestError` 传递 `message`、`request_id`、`code`、`status`，结构化信封失败时回退到 action + HTTP status。它没有按 publication code 建立稳定 registry，也没有严格验证 `details` 的内部 shape。
- Workspace mutation 从 canonical `context.work.revision` 形成 expected revision（`frontend/src/domains/publication/publication-workspace-actions.tsx:139-180`）；任何 409 都在 `:193-227` 设置 stale。表单、备注和上传文件保留，动作禁用，用户点击显式 reload（`:271-299`）。这满足通用 no-replay，但把 `REVISION_CONFLICT`、`REPAIR_TASK_EXISTS`（repair workspace 不在该组件）、`PUBLICATION_CONTEXT_INCOMPLETE`、其它业务 409 混为一种 UI 状态。
- Issue workspace repair/resolve mutation 传 `expected_issue_revision`/`expected_revision`（`frontend/src/domains/publication/published-content-issue-workspace-actions.tsx:61-76`），`handleError` 在 `:158-162` 对所有 409 设置 stale，reload 时同时刷新 workspace 与 lazy repair context（`:164-177`）。没有 `REPAIR_TASK_EXISTS` 消费或 existing task handoff；也没有 code-specific distinction。
- Start dialog 只对 `IDEMPOTENCY_CONFLICT` 清空 idempotency key，所有 409 都调用 `onConflict`（`frontend/src/domains/publication/start-publication-dialog.tsx:102-112`）。`PublicationWorkPage` 对该回调失效 summary/work list/content projection，但 ready query 使用 `refetchType: 'none'`（`frontend/src/domains/publication/publication-work-page.tsx:82-103`）。这是 T6 要审计的 projection recovery path；不能在 T5 code/status 决策前扩大或收窄。
- Article open issue dialog 对任意 409 设置 context stale、保留输入并显式 reload（`frontend/src/domains/publication/published-article-detail-page.tsx:275-303`）；Article 初始 GET 的 404/403 有专用标题，409 与未知错误共用 generic failure/retry（`:418-435`）。

#### GEO

- `frontend/src/domains/geo/geo.api.ts:33-42,362-392` 保留 status/detail，结构化信封失败有 action + HTTP status fallback；optimization mapping `:260-310` 解析 structured field errors、code、request ID，并以 status 409 标记 stale。
- New Observation 只对 `GEO_PUBLICATIONS_CHANGED` 设置 candidate stale（`frontend/src/domains/geo/new-geo-observation-page.tsx:152-203`），显式重读 candidates 后清除 stale，保留仍有效的表单值。这与“未知/其它 409 不应伪造候选集合已变”的边界一致。
- Correction 明确 `conflictCodes = {'GEO_PUBLICATIONS_CHANGED','REVISION_CONFLICT'}`（`frontend/src/domains/geo/geo-observation-correction-page.tsx:79`），提交失败 `:170-186` 保存 fields/form message/request ID；`:203-220` 显式 refetch，按 Published Article ID 合并并在 chain tail 改变时更新 canonical URL。该页面已是 code-specific 409 recovery 的参考实现。
- GEO candidate list、observation delete 等 API tests 保留 409 status/code/request ID（`frontend/src/domains/geo/geo.api.test.ts:247-265,302-318`），但不覆盖每个页面对 `GEO_OBSERVATION_CONTEXT_INCOMPLETE`、`GEO_OBSERVATION_HAS_SUCCESSOR` 或未知 500 的不同 UX。

### 6. 测试覆盖、错配与明确缺口

1. **后端合同覆盖强，code 语义覆盖弱。** `backend/tests/unit/test_contract.py:100-315` 与 runtime 测试 `:444-502,778-840` 冻结 operation/status/schema/header/计数；`test_runtime_request_context_covers_all_operations_and_responses`（`:639-682`）及 merge comparator（`:685-695`）覆盖 metadata 不漂移。但这些测试不验证 `REPAIR_TASK_EXISTS`、`PUBLICATION_CONTEXT_INCOMPLETE`、`REVISION_CONFLICT` 在每个 operation 上的 code/details；若 T5 要求 exact wire，必须补 endpoint-level integration/contract assertions。

### 7. T5 → T6 的边界与 contract-first 原子同步顺序

**T5 完成前不得进入 T6 frontend 409 recovery projection reconciliation。** T6 需要知道每个 409 code 是否代表可采用现有 canonical projection、仅需 stale/reload、还是不可恢复的 context integrity failure；在 `REPAIR_TASK_EXISTS` 的 response details、是否返回 existing task identity、以及 projection invalidation 范围未由 T5 冻结前，前端任何针对该 code 的 reconciliation 都会把业务假设写死。当前 generic 409 stale 逻辑可作为安全的 no-replay 兜底，但不是 T6 的完成标准。

建议按以下原子顺序落地（每一步完成并验证后才向后推进）：

1. **T5 domain/error decision：** 对 `REVISION_CONFLICT`、`REPAIR_TASK_EXISTS`、`PUBLICATION_CONTEXT_INCOMPLETE`、`GEO_PUBLICATIONS_CHANGED`、其它预期 409 逐一确定：status 是否仍 409、稳定 code、`details` 字段与可否携带 existing resource ID、是否允许 retry/reload/reconciliation、失败时哪些状态/投影必须保持不变；同时明确未知 500 继续非合同化。该决策必须写成单一 owner 的合同条目，不创建前端第二套 code/type registry。
2. **OpenAPI/database contract（如确有变化）：** 先更新 `contracts/openapi.yaml` operation status 或 ErrorDetail/details schema；code-only 名称若仍为 string 不应制造无必要 schema 变化。若 operation status 集合改变，逐个检查 publication/GEO path，保持 400 与 request-ID header 规则，不添加默认 500。
3. **Backend route/service 与运行时 owner：** 使 router `responses`、service `AppError`、锁内状态不变性、details payload 与 OpenAPI 同步；runtime metadata 仍由 `backend/app/main.py` 统一负责，不能在业务 handler 重复生成 request-ID。若 status 改变，更新 `backend/tests/unit/test_contract.py`、`WAVE_3_EXPECTED_STATUSES`、计数/comparator；若只改 code，新增 integration exact-code assertions，不能改 metadata merge。
4. **生成客户端：** 以 OpenAPI 为输入重新运行项目既有 `openapi-typescript`/contract generation 命令，审查 `frontend/src/shared/api/generated/schema.d.ts` diff；禁止手改 generated 文件。code-only 变化预期无 generated diff，status/details shape 变化才应出现可解释 diff。
5. **Frontend API/parser 与 production consumers：** 先更新 `publication.api.ts`/`geo.api.ts` 的结构化映射（确保保留 status/code/request ID/details），再依 T5 code semantics 修改页面；T6 才处理 Start Publication/Work/Issue/Article 的精确 invalidation、existing repair handoff、保留表单/文件、显式 reload 与 focus。GEO correction 的 exact-code merge 规则可复用其边界，但不得未经 T5 将 generic publication 409 套入 GEO 逻辑。
6. **测试与文档收口：** 增加 backend exact wire/integration（优先 duplicate repair race）、frontend API/component/E2E code-specific tests、未知 500 generic fallback；同步 `docs/frontend-v2/05...` 的错误矩阵和 `08...` acceptance；若稳定规则发生变化再更新 `.trellis/spec/backend` 与 `.trellis/spec/frontend`。最后执行 targeted contract/runtime/typecheck/related unit/E2E，并检查 generated diff 与跨缓存 projection。
