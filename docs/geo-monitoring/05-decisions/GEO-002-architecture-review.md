## 2. ADR 逐项评审

### ADR-001：在现有模块化单体内扩展 GEO

1. **要解决的问题**：计划、回答、事实核验、内容行动和发布复测紧密关联，拆成独立业务服务会增加事务、身份及历史证据的一致性成本。
2. **建议决策**：保留 FastAPI/SQLAlchemy/PostgreSQL 模块化单体；GEO 子域拥有计划、运行、分析、复核和指标规则，复用身份、审计、凭据、文件与事实服务。Redis 只传递任务标识，对象存储只保存字节。Browser 可独立部署为执行服务，业务裁决仍由后端与 PostgreSQL 拥有。
3. **备选方案**：独立 GEO 微服务适用于已证明的安全隔离或容量需求，但目前缺少此收益证据；MongoDB 会引入第二业务状态源；第三方 SaaS 可作受控输入来源，但不足以替代本系统的事实、证据和审批权威。
4. **当前代码/架构冲突**：总体无冲突，[当前架构](../../architecture.md):5 已采用该方向。新增证据与事实引用尚未接入既有生命周期，属于后续必须设计的接入边界（F06、F05）。内容生成器返回严格内容草稿，不能直接充当原始回答采集器；可复用网络和凭据设施。生产 Worker/Scheduler 属于显式启用的 `production-async` profile，配置不证明其当前正在运行。
5. **ADR 是否需修改**：需要补充模块所有权、文件/事实生命周期接入责任、Browser 无业务状态所有权；已追加待批准补充，不另行批准根级合同。
6. **实施风险**：把新行为继续塞入已有大型 `geo_observation.py` 会混合文章关系与回答级语义；遗漏文件清理引用或事实删除检查会破坏历史证据；独立 Browser 若自行维护状态会出现两个裁决者。应按真实领域边界新增模块，并通过既有权威服务管理引用生命周期。
7. **接受/拒绝建议**：建议接受模块化单体原则，保留 Review 待人工决定。当前没有理由选择独立业务微服务或第二数据库。

### ADR-002：人工、API、Browser 使用统一回答级 Run

1. **要解决的问题**：旧 GeoObservation 表达文章搜索及逐篇发布成果关系，不能准确表示重复采样、自动调用失败、尝试链和回答级多对象分析。
2. **建议决策**：新增 Batch、Run 与不可变 AnswerSnapshot，三种采集方式共用回答合同，由冻结 profile/input 区分环境；旧 GeoObservation 保持独立。逻辑采样单元与执行尝试分开，每个逻辑单元至多贡献一个按预定规则选定的业务样本。费用和执行健康度保留全部尝试。
3. **备选方案**：往旧 `answer_summary` 填自动结果会丢失采集和分析边界；三套业务表会复制指标与复核规则。重试可保留同批次追加尝试，或创建显式关联的重试批次；建议前者用于失败采集恢复，但终态批次是否重新投影必须先获得明确业务决策，不能在实现时隐式选择。
4. **当前代码/架构冲突**：新增模型与现状相容；旧洞察的 `analysis_unit=MANUAL_OBSERVATION_PUBLICATION_RELATION` 已明确分母，应保留。目标文档内部仍有逻辑单元唯一性、requested_run_count 与重试新 Run 的冲突（F01）；调度键、预算状态及 Batch 完成规则也未一致（F10）。这些不是现有 Run 实现缺陷，因为新 Run 尚未实现。
5. **ADR 是否需修改**：需要加入统计单位、重试归属与结果选择原则；业务、数据、状态机文档还需对齐计数和终态语义。本轮已写入待批准建议，未修改这些下游合同。
6. **实施风险**：把重试当新样本会改变可见率和稳定性，按成功答案择优会造成偏差；分析失败重新采集会重复消费并改变证据；终态批次任意回退会破坏历史报告；计划编辑可能产生同窗重复批次。
7. **接受/拒绝建议**：支持统一模型，暂缓接受现稿的计数、重试和状态细节。拒绝复用旧文章关系模型或按采集方式建立三套业务事实。

### ADR-003：采集、机器分析与人工复核分别版本化

1. **要解决的问题**：原始回答需要保留，别名、事实或分析器变化后需要重分析，人工修正必须能够追溯到其依据的机器结果。
2. **建议决策**：证据不可变，AnalysisRevision 和 RunReview 追加保存；明确采用唯一当前分析指针。成功发布新分析时原子切换有效结果，失败保留原指针，较旧结果不能覆盖较新成功结果；复核只能作用于当前同 Run 的分析。采集结果、分析执行与派生工作阶段分开；报告冻结实际选用的证据、分析、复核和口径版本。
3. **备选方案**：查询时按“最新成功”计算可以减少一个指针，但仍需统一并发、复核和报告选择规则，无法省掉权威所有者；只追加事件再构建投影会增加当前系统不需要的基础设施。为每次重分析重新采集、覆盖旧机器结论或原始引用均不可取。事实保留可选择强引用阻止删除，或经批准的完整不可变核验快照，推荐先采用强引用。
4. **当前代码/架构冲突**：原则符合现有不可变历史和追加式更正。目标 Run 终态与重分析写状态相冲突（F02）；当前指针、复核所属 revision 及并发规则未定（F03）；不可变原始引用混入派生分类（F04）；单一事实版本不能覆盖多产品声明，且 SET NULL/删除命令会丢失核验依据（F05）。
5. **ADR 是否需修改**：需要明确状态层次、当前指针、原子发布/复核规则、派生引用所有权、多产品事实绑定及分析哈希覆盖范围；已补充 Review 建议。具体表和 API 仍待后续合同评审。
6. **实施风险**：迟到分析夺取当前结果、旧复核错误覆盖新分析、失败重分析令原有效结果消失、别名升级无法重算引用归属、删除事实后无法解释历史判定；仅冻结哈希或 UUID 不能恢复已删除内容。
7. **接受/拒绝建议**：支持三层版本化，暂缓接受现稿；拒绝覆盖原始证据、将新分析失败静默映射为旧结果成功，或让多个模块各自决定“当前有效”。

### ADR-004：核心版不提供统一 GEO 总分

1. **要解决的问题**：可见度、推荐、引用、准确性和数据质量具有不同分母与风险含义，单个加权分数会遮蔽严重错误、环境差异及样本不足。
2. **建议决策**：提供独立指标、分子/分母、资格与排除原因、样本等级和下钻；管理摘要保留各维度，不压缩为不透明单值。未知值和不足样本明确表达，不补零。
3. **备选方案**：固定加权 0–100 分便于排序，但权重缺乏业务依据；雷达图或指标组可作为展示，不能取代口径；未来确有决策用途时可另立 ADR 批准透明综合指数，并保留组成项与版本。
4. **当前代码/架构冲突**：原则无冲突，现有 GEO 洞察已支持分母、样本不足及 UNJUDGEABLE 排除；旧变化率合同不能随新指标静默改变。目标 PRD 与指标文档有三类分母冲突，分析成功率混用了 revision 数和 Run 数（F09）；因此具体公式不能因接受此 ADR 而被视为冻结。
5. **ADR 是否需修改**：需要明确“接受无总分原则不等于接受全部指标公式”，要求唯一版本化指标字典。已追加建议，具体分母仍需产品裁决。
6. **实施风险**：同名指标返回不同值、重分析次数提高所谓成功率、无序推荐被当作已排序结果、回答级与文章关系样本混合，都会误导机会规则和复测结论。
7. **接受/拒绝建议**：建议接受无统一总分原则；暂不接受冲突公式。核心版拒绝无明确权重、分母与解释的统一评分。

### ADR-005：按人工 → API → Browser 分阶段启用

1. **要解决的问题**：同时建设领域模型和 Browser 自动化会叠加账号、条款、DOM、验证码、预算和故障恢复风险，难以区分采集错误与分析错误。
2. **建议决策**：先验证统一人工证据与分析闭环，再启用经批准的 API，最后启用隔离 Browser 服务；采集面、环境和模式分别统计。发送前必须由数据库当前租约与阶段裁决资格；外发数据必须具有服务端分级/批准依据。
3. **备选方案**：永久人工无法满足自动计划目标；Browser 优先会先承担最不稳定边界；API-only 可交付中间增量，但不能代表真实界面效果，也不能自动满足完整首发 PRD；第三方服务仍需逐平台授权、证据和环境合同。
4. **当前代码/架构冲突**：阶段路线相容，现有 pinned transport、凭据加密和保守 Worker 恢复可复用。目标允许 NOT_STARTED 恢复，但缺少强制发送资格隔离（F07）；INTERNAL 外发表与测试、当前 PUBLIC 边界冲突（F08）；“Browser 非 R1–R6 阻断”与完整首发门禁需区分（F11）。当前部署不存在 GEO 专用队列、开关或 Browser 服务。
5. **ADR 是否需修改**：需要明确中间增量与完整首发的区别，禁止把 adapter 批准等同于数据外发批准，强制发送前 SENT/lease 校验，明确试点也需合规批准；已追加待批准补充。
6. **实施风险**：旧 Worker 在恢复后继续发送导致重复调用/费用；网络调用资格检查遗漏非公开上下文；账号未经批准投入试运行；把 API 结果当 Browser 效果；提前宣称完整核心版上线。
7. **接受/拒绝建议**：有条件接受分阶段原则。发送隔离与外发政策未明确前，拒绝更激进的自动恢复和 INTERNAL 第三方外发；产品负责人未批准范围变更前，保留 PRD 首发门禁。

## 3. 具体发现与安全修订方向

以下 P1 表示应在相关模型/合同被接受并实施前解决的设计问题，不表示现有线上已有该缺陷；P2 表示需明确的边界或基线差异。每项均给出触发条件、影响及可操作的修订方向。

### F01 [P1] 逻辑采样单元与重试尝试未形成一致计数合同（ADR-002）

- 位置：[领域模型](../02-business/02-domain-model.md):255、同文件 `:284`；[数据架构](../03-technical/02-data-architecture.md):325；[重试规则](../02-business/03-workflows-and-state-machines.md):134。
- 触发：同一问题/profile/repeat_index 的失败调用创建 attempt_no + 1 的新 Run。领域模型要求 requested_run_count 等于实际 Run 数，数据模型却已按 attempt_no 区分唯一运行单元；批次终态后如何追加尝试也未定义。
- 影响：固定矩阵的样本总数、进度及分母会随恢复操作变化；筛选多次尝试中的“最好答案”会引入样本偏差。
- 修订方向：定义逻辑 cell、初始请求数和尝试数；费用/健康度使用尝试，业务指标按预定规则每 cell 选择至多一个结果。明确同批次重试对终态的影响，或改用关联重试批次；分析失败不创建采集尝试。修改问题或环境创建新批次。

### F02 [P1] Run 终态与重分析状态推进矛盾（ADR-003）

- 位置：[Run 状态机](../02-business/03-workflows-and-state-machines.md):109、[领域终态不变量](../02-business/02-domain-model.md):288、[Analysis Worker](../03-technical/05-worker-and-collector-architecture.md):346。
- 触发：COMPLETED Run 重分析后出现低置信度，Worker 按当前步骤将其写为 NEEDS_REVIEW；或 ANALYSIS 失败使 Run FAILED 后需要只重分析保存的答案。
- 影响：一方合同禁止终态更新，另一方依赖更新；实现会选择回退终态、绕过触发器，或错误重采集，且 Batch 投影不再稳定。
- 修订方向：推荐采集结果与分析执行独立建模，工作阶段/指标资格作为服务端派生结果；若坚持单一状态机，必须显式修订合法重分析边、终态含义和 Batch 投影，而不能在 Worker 局部例外放行。

### F03 [P1] 当前分析与复核缺少唯一并发选择规则（ADR-003）

- 位置：[当前分析选择](../03-technical/02-data-architecture.md):398、[复核选择](../03-technical/02-data-architecture.md):466、[复核请求](../03-technical/03-api-contract-design.md):287；Run 字段表从 [数据架构](../03-technical/02-data-architecture.md):296 开始，尚无 expected_run_revision 对应字段。
- 触发：两个重分析反序完成，或用户查看 revision 2 后提交复核时 revision 3 已成为当前结果。
- 影响：迟到结果覆盖新结论；按整个 Run 的最新 review 选择会套用旧分析的修正；API 并发条件缺乏持久化权威。
- 修订方向：采用显式当前分析指针和受控协调 revision；发布时锁定 Run、校验同 Run 归属及递增版本，防止较旧成功结果覆盖较新结果。创建命令校验预期当前版本，复核命令锁内核验 Run/analysis/revision，限定当前分析内的有效 review。新分析成功发布才使旧复核失效；失败保留原有效结果，新的待复核结果按规则排除。报告冻结实际使用的 ID 和口径版本。

### F04 [P1] 原始引用表承载可重算派生结论（ADR-003）

- 位置：[geo_answer_citations](../03-technical/02-data-architecture.md):370，source_category 与 matched_subject_id 被放入原始回答引用表；[不可变防线](../03-technical/02-data-architecture.md):527。
- 触发：别名、域名或文章映射变化后重分析同一回答。
- 影响：不可变原始引用无法更新分类，AnalysisRevision 又没有独立归属结果；系统只能使用过时分类或破坏原始证据。
- 修订方向：原始 URL、顺序、采集标题/片段保存在证据层；分类、subject/文章匹配保存为 AnalysisRevision 所有的引用判定并由 review 覆盖。不要将原始表中的唯一分类视为所有 revision 的权威。

### F05 [P1] 多产品事实绑定及删除语义不足以保留核验依据（ADR-003/001）

- 位置：[单一分析 fact_version_id](../03-technical/02-data-architecture.md):390、[claim 外键](../03-technical/02-data-architecture.md):437、[重分析 API](../03-technical/03-api-contract-design.md):274、[输入哈希](../02-business/02-domain-model.md):352；当前 [delete_fact_version](../../../backend/app/services/product_facts.py):571。
- 触发：一个回答涉及多个我方产品；只升级 analyzer_version；或删除仅被新 GEO 分析引用的已批准事实版本。
- 影响：单一事实版本不足以判断跨产品声明，hash 不含分析配置会复用旧结果。当前删除命令只检查 ContentTask/ContentVersion，新分析 FK 又为 SET NULL，核验依据可能丢失；如同时禁止 UPDATE，FK 置空也会撞上不可变触发器。未知竞品事实不能因此猜测。
- 修订方向：按 subject/Product 冻结同产品、非空 APPROVED FactVersion 绑定及规则；claim 关联正确产品事实，无依据保持 UNJUDGEABLE。hash 覆盖答案、别名/域名快照、所有事实绑定和分析器/模型/提示/规则配置。默认将新引用纳入事实删除阻断并用 RESTRICT；若选择完整冻结核验快照，先明确其保密、保留与删除授权。UUID、哈希和短 excerpt 不足以替代完整依据。

### F06 [P1] 新证据外键尚未接入 FileRecord 清理权威（ADR-001/002）

- 位置：[文件引用检查](../../../backend/app/services/file_records.py):238、[清理声明](../../../backend/app/services/file_records.py):303、[新证据字段](../03-technical/02-data-architecture.md):352、[现有数据库合同](../../../contracts/database.md):75。
- 触发：后续保存 AnswerSnapshot 的 screenshot/raw_payload 外键，却未同步文件清理器；或者删除对象时通过 SET NULL 解除不可变证据引用。
- 影响：现有清理器只识别平台 Logo、发布附件和旧 GEO 附件，可能把新的在用证据当作无引用对象。FK 置空与不可变 UPDATE 防线也可能互相阻断。这是新增模型的接入风险，当前三类引用实现并无本轮确认的遗漏。
- 修订方向：新关联在同一生命周期边界验证 VERIFIED、类别、归属和行锁，并纳入 file_is_referenced。截图保留与 raw payload 到期策略分别定义；若允许到期移除，使用批准的专用保留命令及可追溯记录，不能任由通用 GC 静默擦除证据。

### F07 [P1] NOT_STARTED 自动恢复需要发送前的强制租约隔离（ADR-005）

- 位置：[目标发送步骤](../03-technical/05-worker-and-collector-architecture.md):204、[恢复规则](../02-business/03-workflows-and-state-machines.md):134；当前 [过期 RUNNING 恢复](../../../backend/app/services/generation_dispatch.py):137、[请求发送](../../../backend/app/services/pinned_http.py):232。
- 触发：Worker A 在记录 NOT_STARTED 后暂停；租约过期恢复为 PENDING，Worker B 获得新租约；A 恢复并发送。
- 影响：若 A 发送前未强制校验最新 token/状态并持久化 SENT，两个 Worker 都可能调用外部服务。只保证单进程 transport 不换地址重发，不能证明跨 Worker at-most-once。
- 修订方向：首个请求字节前必须在短事务内核验当前未过期 lease、token、RUNNING 和 NOT_STARTED，再原子置 SENT；恢复撤销旧 token，失效 Worker 不得发送。SENT/UNKNOWN 保守失败，不自动重发；发送前置 SENT 后崩溃允许明确未知结果而非猜测未调用。不能建立此保证时，保留当前过期 RUNNING 明确 FAILED/WORKER_LOST 的恢复方向。外部分析模型也需要独立调用阶段。

### F08 [P1] INTERNAL 外发政策与当前边界、目标测试冲突（ADR-005/003）

- 位置：[GEO 分级表](../03-technical/06-security-and-compliance.md):43、[安全测试要求](../03-technical/07-testing-and-quality.md):344、[当前外发校验](../../../backend/app/services/generation.py):87、[当前架构](../../architecture.md):35。
- 触发：标为 INTERNAL 的问题/上下文或默认 INTERNAL 的原始答案，因 collector/analyzer 已“批准”而被发到第三方模型；当前 PromptVariant 字段尚未建立相应外发授权依据。
- 影响：安全文档允许批准服务接收这些数据，测试则明确阻断 INTERNAL/RESTRICTED 外部分析，实施者无法同时满足二者。当前内容生成 PUBLIC 边界不能靠复用供应商客户端自动扩宽。
- 修订方向：区分公司受控内部分析服务与第三方服务；明确问题、附加上下文、事实和答案的 PostgreSQL 分级/批准依据及冻结规则。未知或非公开内容默认不向第三方发送；原始答案若默认 INTERNAL，采用受控内部分析/人工路径，或经明确规则重新分级批准。若业务要求例外，须另获安全政策决策，adapter 批准不代表数据批准。禁止放宽既有内容生成外发合同。

### F09 [P1] 同名指标分母冲突，分析成功率可能超过 100%（ADR-004）

- 位置：[PRD 指标](../01-product/02-geo-core-prd.md):1201、同文件 `:1210`、`:1213`；[首位推荐率](../02-business/04-monitoring-methodology-and-metrics.md):173、[严重错误运行率](../02-business/04-monitoring-methodology-and-metrics.md):334、[质量指标](../02-business/04-monitoring-methodology-and-metrics.md):368。
- 触发与影响：两个推荐适用样本，一个可靠排序且我方 rank=1、另一个无排序，PRD 口径为 50%，业务口径为 100%。一个严重错误样本加一个无法判断事实的合格样本，PRD 为 50%，业务口径为 100%。运行成功率又分别除以实际创建数和终态数。一个已采集 Run 完成两次成功分析，revision 数除以已采集 Run 数即 200%；若 COLLECTED 只指当前状态，分母还会随分析推进消失。
- 修订方向：产品裁决后按 metric_code 统一统计单位、推荐适用性、有效样本、可判断声明、未知值、排除规则及 formula_version。建议分析覆盖率使用唯一 Run 及当前成功分析，分析尝试成功率另用已终结 revision 作分母；不要混用。准确性 verdict 等枚举也需统一，旧 API 的率和变化率保持原合同。

### F10 [P1] 调度去重、预算状态与 Batch 投影未满足同一业务合同（ADR-002）

- 位置：[调度键](../03-technical/05-worker-and-collector-architecture.md):144、[同窗唯一验收](../01-product/02-geo-core-prd.md):1418、[预算验收](../01-product/02-geo-core-prd.md):1420、[Batch 状态](../02-business/03-workflows-and-state-machines.md):85、[Batch 表](../03-technical/02-data-architecture.md):279。
- 触发：同一 scheduled_at 在修改 plan_revision 后再次调度；批次同时有成功与失败；达到预算停止尚未发出的调用。
- 影响：将 revision 纳入 schedule_identity 可生成两个同窗批次；COMPLETED 的“全终态且至少一个成功”与 PARTIAL 的混合成功/失败重叠；PRD 必需 BUDGET_BLOCKED，但业务/表状态枚举未包含，无法据实施方便选成普通失败。
- 修订方向：以 plan_id 和规范化调度窗口建立权威唯一身份，plan_revision 保存在冻结输入；补充互斥 Batch 投影和预算阻断枚举/语义。若要允许同窗多版本批次或改掉预算状态，先修订并批准产品验收合同。

### F11 [P2] 中间发布增量与完整核心版首发条件应分别描述（ADR-005）
