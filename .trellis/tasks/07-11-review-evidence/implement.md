# 事实与内容审核证据闭环实施计划

## 实施步骤

1. **契约与投影字段**
   - [x] 追踪事实快照、证据、内容版本、生成快照和演员摘要的权威来源。
   - [x] 在 OpenAPI 定义 `ReviewRecord`、`FactReviewContext` 和 `ContentReviewContext`。
   - [x] 明确 `available_actions` 与退回意见校验错误。
2. **后端读取模型**
   - [x] 实现事实审核上下文查询。
   - [x] 实现内容审核上下文聚合查询，保证单次读取版本一致。
   - [x] 按稳定时间与 ID 顺序返回审核历史。
3. **审核命令收紧**
   - [x] `request-changes` 在 Schema 和服务层拒绝空白意见。
   - [x] `submit` / `approve` 保持意见可选并继续追加记录。
   - [x] 服务端质量阻断和状态转换保持最终权威。
4. **前端审核视图**
   - [x] 内容页切换为单一审核上下文查询。
   - [x] 展示正文、质量、差异、冻结事实/证据、替代边界和时间线。
   - [ ] 事实版本支持 URL 深链和审核历史显示。
   - [x] 任一查询失败时禁用审核操作。
5. **测试与文档**
   - [x] 后端测试覆盖历史顺序、演员摘要、空退回意见和历史事实稳定性。
   - [x] 前端组件测试覆盖退回、重新提交、批准、缺证据和查询失败。
   - [x] 更新产品方案与测试文档中的审核读取契约。

## 关键测试

- 退回后创建者刷新仍看到最新意见和完整历史。
- 空白退回意见返回明确 422，提交和批准可不填写意见。
- 后续事实版本或工作区变化不改变旧内容审核上下文。
- Engineer 无需调用用户管理接口即可看到演员摘要。
- 阻断质量问题存在时直接 API 仍不能批准。
- 上下文部分数据缺失时显式失败，不用当前工作区或空默认值补齐。

## 回滚点

- 聚合上下文出现版本错配时停止审核写操作，保留旧数据不变。
- 不回退为前端拼接多请求并猜测缺失字段；修复服务端投影后再恢复。

## Goal 2 完成门禁

- [x] 主 Agent 先更新 OpenAPI 并生成前端类型，后端和前端不手写第二套 DTO。
- [x] 事实与内容上下文均返回稳定顺序的完整审核历史和服务端 `available_actions`。
- [x] 空白退回意见在请求边界和应用服务均失败；submit/approve 可不填意见。
- [x] 后续工作区、事实版本或用户状态变化不改变历史内容审核上下文。
- [x] 组件测试覆盖查询失败、真实空证据、退回、重新提交和批准确认。
- [x] 与发布闭环共同通过 Goal 2 的契约、单元、集成、前端和目标 E2E；本 Goal 不扩展 GEO。
- [x] 完成后停止；不自动提交、推送或进入 Goal 3。

## Goal 2 验证证据

- `FactReviewContext` 与 `ContentReviewContext` 由审核应用服务一次性装配；Router 只映射 HTTP，前端直接消费 OpenAPI 生成类型。
- PostgreSQL 集成测试覆盖稳定历史、演员摘要、空退回意见、缺失证据显式失败、事实退役后历史上下文仍冻结，以及阻断质量问题不能经直接 API 批准。
- 前端组件测试覆盖查询失败时不渲染状态操作、真实空证据、退回必填、重新提交和显式批准确认。
- 最终验证通过：契约检查、62 个后端单元测试、17 个 PostgreSQL 集成测试、8 个前端组件测试、2 个全 UI Playwright E2E 和双端镜像构建。
- 事实审核历史已在事实版本交互中展示；独立事实版本稳定 URL 深链属于 Goal 4 的统一前端路由工作，本任务对应实施项保持未完成，未将规划能力误判为已实现。
