### 3. 事务、副作用和并发测试的可复用证据

- `backend/app/db.py:31-40` 的 `get_db` 在任意请求异常时 rollback、最终 close；全局 `integrity_error_handler` 本身不 rollback。服务内已知 mapper 在 flush catch 内 rollback 后才查询或抛 AppError，例如 product、platform type、platform account、profile、prompt、humanization job。未知异常依赖 request dependency rollback；service-level 测试若捕获异常后继续用同一 Session，必须显式 rollback。
- 审计原子性已有强模板：
  - `test_product_detail.py:248-335` 失败重复不追加 `product.updated` 成功审计；
  - `test_query_topic_list.py:151-220` 对成功 create/update 和 revision conflict 分别验证 AuditLog；
  - `test_identity_management.py:782-798` 只保留成功 request 的删除/重置审计；
  - `test_geo_insights.py:217-231,494-538` 用基线计数断言失败不留下 task、source 或 AuditLog；`test_geo_insights.py:495-538` 还验证已 flush 的 task 在 source flush 失败后整体回滚（当前故障是 RuntimeError，不是 IntegrityError）。
  - `test_audit.py:40-57,85-91` 证明 `append_audit` 只 add、不自行 commit，并禁止失败结果/错误码进入成功审计。
- 并发可复用模式：
  - `test_content_task_creation.py:291-326` 使用两个 SQLAlchemy Session、`Barrier(2)`、`ThreadPoolExecutor(2)`，验证同 key 同 payload 只生成一个 task；
  - `test_geo_insights.py:275-322` 同样验证同 key 只生成一个 task/source，并验证异载荷为 `IDEMPOTENCY_CONFLICT`；
  - `test_ai_channel_management.py:639-800` 通过两个真实 HTTP `TestClient` 并发删除，验证 `[204,404]` 和单次副作用。
- 这些并发测试大多验证 advisory lock/row lock/idempotency，而不是两个连接同时撞同一 unique constraint。后续唯一约束竞态必须使用两个独立 Session/连接和 barrier，控制预检后、flush 前窗口；断言结果集合为“一个成功 + 一个确定的已知领域错误”，唯一行计数为 1，失败请求的 AuditLog/event/revision/关联行均无成功副作用。

### 4. Mock 局限与建议的真实 PostgreSQL sentinel

- 当前没有 `IntegrityError` mock 测试，因此不存在“mock 已证明 mapper 正确”的证据。可新增窄单元测试验证 `constraint_name -> AppError` 的纯分支和 unknown passthrough，但必须把它定位为分支测试，不得替代数据库测试；fake `orig` 无法证明 psycopg 3 的诊断字段、SQLSTATE、事务 failed state 或 PostgreSQL 的冲突等待行为。
- 每个已知唯一映射的 integration test 应分两层：
  1. 通过真实 ORM/service/HTTP 命令触发约束，断言最终 ErrorEnvelope/domain code/details、原记录/副作用；
  2. 在同一隔离数据库另开短事务，用等价参数直接 INSERT/UPDATE（或在 mapper 外层捕获）并断言 `exc.value.orig.sqlstate == "23505"` 与 `exc.value.orig.diag.constraint_name` 为预期值。对 FK 使用 `23503`；CHECK 使用 `23514`；NOT NULL 使用 `23502`；触发器 `55000` 继续按既有 PostgreSQL exception 类型/语义验证，不把它当成 revision 冲突。
- 推荐 unknown sentinel：创建合法渠道后，通过 HTTP `POST /api/v1/ai-channels/{id}/models` 两次相同 `model_id`，真实撞 `AIModel(channel_id, model_id)` 唯一约束；同时以独立 psycopg 事务捕获 `23505`/constraint name。sentinel 需断言返回默认 500、不会是 `REVISION_CONFLICT`、不会返回 SQL/表名/约束名/英文数据库 message；只冻结 status 与安全边界，不把 body/code/header 形状写成公共合同。若未来要提供稳定 JSON 500，再先完成 OpenAPI/产品错误合同决策。
- 可追加第二个 unknown sentinel：同一渠道重复 header name（`createAIChannelHeader`）或重复 content task/version；优先选择 payload 合法且没有前置业务判断的路径，以排除“预检恰好命中”的假阳性。
- 对未知 sentinel 还要检查 session 可恢复性：请求后使用同一 dependency 连接/后续请求不出现 `InFailedSqlTransaction`，数据库中没有半写入；`get_db` 的 rollback 责任由 `backend/app/db.py:31-40` 承担，但应由 HTTP integration 观察。

### 6. Optional validation 与一次性 gate

- 影响仅限后端实现且公共合同不变时，`make typecheck`、`make lint`、完整 `backend/tests/unit` 与不相关 integration 可作为 optional；已存在的前端完整测试、E2E、构建也不应替代 T1–T5 的真实 PostgreSQL 命令。
- 若 contract/status/generated client 改动，完整 `make contract-check` 和 T6 受影响 frontend consumer/typecheck 不再 optional；若共享错误边界、跨领域 mapper 或公共 response contract 改动，再把 `make test-integration`（即 `backend-test` 全部 125 个定义）列为 required。
- 最终全范围 gate 只能在所有 targeted checks 通过后运行一次：`make verify`（包含 contract、lint、typecheck、unit、integration、build、E2E 和 deploy checks）。按项目全局停止条件，gate 失败后不得在同一回合自动重跑；只允许最多两次 `repair -> targeted re-check`，独立 review 一次、最多一次定向复审。相同根因再次出现或第二次仍失败时停止并报告证据、当前 diff/state 和选择，不继续循环。
- 本研究没有运行上述测试，原因是任务明确为只读审计；命令中未含数据库清理或 Git 操作。真实集成 fixture 自行创建/销毁随机数据库，仍需确认测试账户具备 `CREATE DATABASE` 权限。

## Caveats / Not Found

- 未发现任何测试直接断言 SQLAlchemy `IntegrityError.orig.diag.constraint_name` 或 `.sqlstate`；当前的真实 PostgreSQL 测试虽能触发 UniqueViolation/CheckViolation/DBAPIError，但大多只断言异常类型或领域结果。
- 未发现手工 mock `IntegrityError`；未来若增加 fake diagnostic 单元测试，只能覆盖分支，不能证明 PostgreSQL 约束身份、事务 failed state、锁等待和真实 HTTP rollback。
- 未发现针对 `createPlatformProfile` duplicate slug、`createPlatformPrompt` duplicate name、`createHumanizationJob` 其他 IntegrityError 分支的现有 integration domain assertion；它们当前分别依赖回查或存在即推断，无法证明 unknown 约束安全。
- `createAIModel` 的合法重复 `model_id` 是最小 unknown sentinel 候选；T1 已选择恢复框架默认 500，只固定 HTTP status 与不泄漏边界，不预设新 error code/body/header，也不要求先改 OpenAPI/runtime/generated/frontend。若未来要把该 500 变成稳定业务信封，才另行执行 contract-first 决策。
- 没有运行测试、没有修改生产代码/测试/合同/迁移，也没有执行 Git 操作；本文件是本 Task 唯一研究写入。
