### 真实调用链与当前状态

1. FastAPI runtime schema 的 owner 是 `backend/app/main.py`：全部业务 router 在 `main.py:333-341` 注册；`_custom_openapi()` 先调用 FastAPI 官方 `get_openapi()`，再合并跨切面 metadata 并缓存（`backend/app/main.py:344-353`）。它不读取冻结合同，因此 runtime 与 static 是独立来源。当前 builder 的合并责任包括组件、每个 operation 的请求 `X-Request-ID`、显式 400、以及全部 response 的 response header（`backend/app/main.py:155-180` 及其后续 merge 分支）。middleware 负责生成/校验请求 ID 和回写 response header（`backend/app/main.py:264-275`）；它与 schema builder 是同一 cross-cutting owner 的运行时/文档两面。
2. 错误 response 的 schema/status owner 仍是调用方显式传入：`error_responses(*status_codes)` 只为列出的状态绑定 `ErrorEnvelope`，不推断额外状态（`backend/app/errors.py:16-21`）；handler 以四字段 `ErrorEnvelope` 序列化实际业务错误（`backend/app/errors.py:41-54`）。这与归档 waves 的“只修 route decorator metadata、不改业务控制流”边界一致。
3. comparator 已具备纯 API：`compare_response_contracts(contract_document, runtime_document)` 不读文件、不访问 app、不修改输入（`backend/app/tools/contract_check.py:1363-1373`）。但默认 `check()` 仍在 `backend/app/tools/contract_check.py:1376-1430` 走 legacy security/path/operationId/参数/request body 检查，并在 `:1420-1429` 通过 `successful_response()` 仅比较首个成功 response；该函数定义和唯一生产调用点分别为 `:149`、`:1420`。因此当前工作树证据显示 Phase F 尚未把完整 comparator 接入默认 gate。
4. CLI 仍有两条执行路径：`--response-report` 在 `backend/app/tools/contract_check.py:1437-1463` 加载 static contract、复制 `app.openapi()`，调用同一纯 comparator，完整漂移返回 1、无漂移返回 0、无效/unsupported 返回 2；无 flag 则在 `:1464-1468` 调用旧 `check()`。现有单测仍直接覆盖该 transitional flag（`backend/tests/unit/test_contract_check.py:667-760`）。

### Makefile、CI 与 frontend canonical generated check

- `Makefile:13-18` 确立 canonical 顺序：`contract-generate` 只执行 `npm --prefix frontend run api:generate`；`contract-check` 先执行 `uv ... python -m app.tools.contract_check contracts/openapi.yaml`，再执行 `npm --prefix frontend run api:check`。当前没有将 `--response-report` 作为独立 Make target 或参数，因此 Phase F 只需改变 checker 的默认 `check()` 语义即可让同一 target 成为完整 response gate。
- `.github/workflows/ci.yml:1-5` 的 CI 仅由 `workflow_dispatch` 触发；verify job 在安装、迁移后于 `:53-57` 调用一次 `make contract-check`，随后在 `:58-77` 执行 lint/typecheck/unit/integration/build/E2E/deploy checks。CI 没有重复调用 backend checker，也没有单独调用 `--response-report`；独立 `frontend-test` job 仅在 `:79-93` 运行 Vitest shard，不改变合同门禁顺序。
- `frontend/package.json:19-20` 定义 canonical 生成与检查：`api:generate` 从 `../contracts/openapi.yaml` 生成 `src/shared/api/generated/schema.d.ts`，`api:check` 调用 `scripts/check-openapi.mjs`。后者在 `:7-28` 使用临时目录重新运行同一 `openapi-typescript`、逐字节比较 committed generated 文件并在 `finally` 清理临时目录；不读取 FastAPI runtime schema，也不执行 response comparator。因而顺序是“冻结合同/后端 checker → generated bytes check”，frontend check 不能替代 runtime-vs-contract gate。
- `backend/pyproject.toml:37-39` 将相同模块暴露为 `partsignal-contract-check`，但 Makefile/CI 使用模块调用；没有发现其它生产调用方。`rg` 仅在测试和历史任务中找到 `--response-report`。

### 归档阶段、零漂移基线与 Phase F 依赖

- Phase A `08-31-response-comparator-core` 的规划/实现明确要求纯 comparator 和无过滤 `--response-report`，保持默认 `check()`、首个 2xx shortcut 和 `make contract-check` 不变（归档 `prd.md:5-7,27-28,41-43`；`implement.md:28-29,44-58`）。这解释了当前双路径，而不是遗漏的第二个正式 gate。
- Phase B 冻结合同 authority reconciliation 明确不改 runtime、`check()`、Makefile/CI，report 在后续 metadata 未完成时应为 1（归档 `09-01-frozen-contract-authority-reconciliation/prd.md:25-38,51-61`；`design.md:97-107`）。Phase B 后的 schema composition repair 又要求 15 个闭合 `allOf` 组件展平为可实例验证的 object，禁止过滤/overlay/private hook（归档 `09-02-response-schema-composition-authority-repair/prd.md:21-45`；`design.md:14-24,60-85`）。
- 三个 runtime metadata waves 分别覆盖 61、58、43 个 operation；Wave 1/2 在后续 wave 尚未完成时允许全局 report 为 1，Wave 3 在 GEO identity 和 publication event-time 前置修复后要求全局 report 归零。Wave 3 归档实现记录三波联合测试必须分别得到 `[]`，以及无过滤 report rc=0（`09-02-runtime-response-metadata-wave-3/implement.md:80-95`；`prd.md:17-21,40-55`）。
- GEO identity repair 关闭 5 个 operation 的 3 个 discriminator drift（`09-02-geo-response-schema-identity-repair/prd.md:5-16,32-42`）；publication event-time repair 解决 PostgreSQL 与 Python 跨时钟造成的 HTTP 前置 sentinel 失败，归档记录独立修复 `562d2bce`、归档/日志证据 `b2f80c3a`/`08cec203`，恢复后四个 PostgreSQL sentinel `4 passed`（`09-02-runtime-response-metadata-wave-3/implement.md:78-82`；`09-02-publication-event-time-order-authority-repair/research/validation-results.md:3-20`）。这两项是 Wave 3 可被信任为零漂移的关键前置，而不是 Phase F 本身。
- Phase X cross-cutting task 将 162 个 operation 的请求 Header、显式 400 和全部 response `X-Request-ID` Header 合并到 static/runtime/generated，研究记录两侧均 162 operation、861 个原 response occurrence、增加后 1023 个 occurrence，comparator/report 为 0（`09-02-cross-cutting-request-context-metadata/research/request-context-authority-audit.md:3-7,24-36`）。其 required validation 顺序也明确先 `make contract-check`、再无过滤 report、然后 canonical generate/check/typecheck（`implement.md:32-58`）。它明确不修改默认 `check()` 或 `successful_response()`，把最后切换留给 Phase F（`design.md:56-70`）。
- 父任务 Phase F 是唯一剩余集成动作：在 `08-31-non-2xx-contract-check/implement.md:179-205`，要求 `check()` 调用完整 comparator、删除 `successful_response()` 和首个 2xx shortcut、删除仅供过渡的 report-only 入口、确认 162 operation 的 status/media/header/schema 零漂移，并确认 Makefile 先 backend 后 frontend、CI 继续只调用 `make contract-check`。该段明确预期文件只有 `backend/app/tools/contract_check.py` 和其聚焦测试，Makefile/CI 预计零改动。

### `--response-report` 去留建议

建议在 Phase F 激活时删除 `--response-report` 这一 transitional CLI 分支及其仅为该分支存在的入口逻辑，同时保留 `compare_response_contracts()` 纯 API 和测试 seam。依据是父任务 Phase F 的明确清单（`implement.md:190-192`），以及当前没有 Makefile/CI/生产调用方消费该 flag；保留它会继续暴露“旧默认 gate + 完整 report gate”两套生产可见语义，增加误把 report 当正式门禁或绕过默认门禁的风险。删除前应把单测从“flag 分支退出码”改为覆盖默认 `check()` 的完整 comparator 行为；纯 comparator 的 mutation/instance 测试仍应保留。

不建议修改 Makefile、CI 或 frontend canonical scripts：当前调用链已经满足父任务要求，`Makefile:16-18` 和 `.github/workflows/ci.yml:53-61` 只需等待默认 checker 语义切换；frontend `api:check` 是冻结合同到 generated bytes 的独立可复现证明（`frontend/scripts/check-openapi.mjs:11-28`），不应被改造成 runtime 比对器。修改这些只读集成文件会重复 gate、改变现有手工 CI 触发策略，且违背 Phase F “Makefile/CI 预计零改动”的范围。

### 任务/提交证据的解释边界

- 九个归档 `task.json` 均显示 `"status": "completed"`，但 `"commit": null`；除 Wave 3 `task.json` 另有 `baseline_commit` 字段外，不能把 Trellis archive metadata 当作已验证 Git commit 证明。归档正文中出现的历史 hashes（如 `4ccd6ea7`、`89245be8`、`562d2bce`、`08cec203`）只能按任务记录中的历史证据引用；本研究未执行 Git 操作，未独立验证这些 refs。
- publication event-time 的 `task.json` `parent` 为 null，而其研究/设计正文说明它是 Wave 3 的独立前置；因此不能只依赖 parent 字段重建完整依赖图。其归档 research/validation 记录仍可作为“修复 owner 与 sentinel 结果”的阶段证据。
- 归档任务中的部分 PRD/implement checklist 是规划时状态（例如 Phase X PRD 中若干 `[ ]`），而同任务 research/validation 或后续 Wave 3 记录了运行结果；应优先按具体 validation 段落和当前源码交叉判断，不把 archive status 或未勾选项单独解释为当前失败。
- Trellis 研究角色禁止加载 `implement.jsonl`、`check.jsonl`；本审计只确认这些 manifest 存在并读取 `task.json`/Markdown/源码，未将被禁止的 JSONL 内容作为证据。manifest 截断 warning 也不能被当成产品 contract drift。

- 未发现需要修改的集成文件、前端生成脚本或稳定规范。允许写入范围仅为本研究文件；所有源码、合同、Makefile、CI、frontend 脚本及父/归档任务文件均保持只读。
